# 万级至完整模型的板端整幅渲染

2026-09-26，悟净 30TAI Lite。**完整官方 train 场景的 559,263 个不同 Gaussian 已在板端参与整幅图像光栅化**，不是原来 4 点 Tile 的扩充描述。FPGA 路径由板端 ARM 求值 `power/exp/alpha`，GSB1 FPGA 执行有序的透明度、颜色合成；单核和四核纯 ARM 实际运行相同的帧输入。输出由板端回读，见 [640×356 实际渲染图](previews/n559263_v0_w640.png)和[四种规模对比](previews/scale_comparison.png)。

## 计算范围与数据

使用既有官方预训练 train/iteration_7000 PLY，SHA256 `8212d03d01edc66423fdd8a6e9884f5f73838cccdda1c82dbf2aea514eb0dce7`。GPU 端经锁定的 GraphDECO CUDA 实现生成投影、SH 颜色、Tile 重复列表、全局深度排序及对应官方输出；每组输入/Golden 的哈希见 [manifest](data/20260926T135717/manifest.json)。10k/50k/100k 是固定种子的嵌套子集，均是不同的模型 Gaussian，不通过重复同一点凑数；子集直接删点，因此画质下降和空洞并非压缩方法的性能结论。完整模型包括同一视角两种分辨率和第二视角。

板端读取已准备的完整帧属性及有序列表，**实际计算每个像素的候选 Gaussian `power`、`exp`、alpha 剪枝、提前终止和颜色合成**。计时包括颜色定点打包、CPU 处理、SDK 寄存器装载/等待/回读，不包括输入文件读取、SDK 初始化、输出落盘、SSH、显示和 GPU 投影/SH/分组/排序。因此表中为**已准备帧的光栅化吞吐**，绝非 Camera Pose→Framebuffer 端到端帧率，也不是板端在线训练或摄像头输入。当前 NPU 没有参与这批测试，未使用 DMA。

GSB1 每批物理容量 256 条命令。5,355,523 条命令（完整模型视角 0，320×178）是连续提交的 20,921 个批次，并非一个超大硬件批。处理所有像素之前并不知道是否会提前终止；“进入 Tile 列表”“真正访问”“实际合成”是三个不同计数。

## 同输入板端性能

以下 320×178 均为同一板卡、同一冻结二进制、每后端一次预热后三次完整帧计时的均值，单位秒/帧。各路径都输出 56,960 个像素。CPU-FP32 路径直接以 FP32 合成；CPU-fixed 使用和 FPGA 相同的冻结 Q30/Q24 合成契约。四核路径是 OpenMP Tile 并行，FPGA 路径的求值仍为单核 CPU。

| 输入不同 Gaussian | CPU FP32 1 核 | CPU fixed 1 核 | CPU FP32 4 核 | CPU fixed 4 核 | CPU+FPGA | 实际访问不同点 | 实际贡献不同点 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 10,000 | 0.609 | 0.632 | 0.157 | 0.164 | 1.777 | 8,139 | 8,057 |
| 50,000 | 3.122 | 3.281 | 0.827 | 0.855 | 6.734 | 40,832 | 39,902 |
| 100,000 | 5.587 | 5.972 | 1.607 | 1.702 | 11.515 | 81,519 | 71,680 |
| **559,263** | **22.645** | **23.664** | **7.614** | **8.135** | **38.840** | **362,996** | **221,026** |

完整模型视角 0 的 640×356 图像已实际测试一次：CPU FP32 1/4 核 **38.874/11.713 s**，CPU fixed 1/4 核 **42.099/12.835 s**，CPU+FPGA **98.658 s**。此组是单次校准，不给出稳定分位数或置信区间。第二完整视角的三次重复数据见下表及版本 CSV；不同视角不合并计时。

| 其他完整模型视角 | CPU FP32 1 核 | CPU fixed 1 核 | CPU FP32 4 核 | CPU fixed 4 核 | CPU+FPGA | 访次/贡献次 |
|---|---:|---:|---:|---:|---:|---:|
| 视角 10，320×178 | 19.349 | 19.918 | 6.255 | 6.446 | 31.905 | 96,864,505 / 4,077,340 |

完整模型视角 0、320×178 的每帧实际访问 118,468,079 个 Gaussian–pixel 候选、合成 5,202,912 次、38,691 像素触发提前终止。单核 CPU 的 22.645 s 和约 100% 的进程 CPU 使用率证明大场景确实产生计算压力；四核降至 7.614 s，但仅此已准备帧仍约 0.131 帧/秒，远未实时。

该完整视角的四核 FP32 三次值为 **7.508、7.509、7.824 s**，平均/中位/P95/P99 为 **7.614/7.509/7.792/7.817 s**；CPU+FPGA 三次为 **38.828、38.838、38.853 s**，平均/中位/P95/P99 为 **38.840/38.838/38.852/38.853 s**。这是同一帧短时间重复运行，不是三个独立场景；样本太少，不把 P95/P99 解释为稳定尾时延。四核 CPU 进程占用约 **400%**（以一个核为 100%），单核/FPGA 路径约 **100%**；主视角各运行峰值 RSS 约 **47–50 MiB**，不含操作系统缓存及共享内存占用。

FPGA 对同一输入的 38.840 s 中，SDK 批装载平均 **13.849 s**，等待 **0.958 s**，回读 **0.345 s**；其余约 **23.687 s** 包含 CPU 高斯求值、`exp`、命令构造及软件调度。FPGA 执行计数 **95,196,795 cycles**，在 100 MHz 下约 **0.952 s**，包含在等待中，不能加到总耗时两次。每帧平均 **32,294,703 次寄存器写**、约 **2,372,852 次读**，仅逻辑寄存器字节即约 **139 MB**；完整帧输入文件为 **24.4 MB**。这证明现有主要瓶颈不是合成算术本身，而是 CPU 求值加逐命令供数。单核 fixed 23.664 s 仍比 CPU+FPGA 快约 1.64 倍；四核 FP32 7.614 s 则快约 5.10 倍。扩大场景不能单靠既有批接口获得加速。

## 正确性与画质

每条后端和官方 CUDA 同输入逐像素比较：RGB 最大误差 `<=1e-4`、平均 `<=1e-5`，透射率 T 最大 `<=1e-5`，最后贡献项 ordinal **完全一致**。**FPGA 与 frozen fixed CPU 在六组完整图像输入上的状态逐字段精确一致**，多次输出也稳定；这证明定点合成硬件执行正确，但不自动证明与官方 CUDA 的严格等价。

| 输入 | FP32 CPU→官方门槛 | fixed CPU/FPGA→官方门槛 | fixed CPU↔FPGA |
|---|---|---|---|
| 10k，视角 0，320×178 | 通过 | 通过 | 精确一致 |
| 50k，视角 0，320×178 | 未通过：T max 超过 1e-5 | 未通过：T max 2.2471e-5 | 精确一致 |
| 100k，视角 0，320×178 | 未通过：1 像素 last 不同 | 未通过：1 像素 last 不同 | 精确一致 |
| 完整，视角 0，320×178 | 通过 | 未通过：2 像素 last 不同 | 精确一致 |
| **完整，视角 10，320×178** | **通过** | **通过** | **精确一致** |
| 完整，视角 0，640×356 | 通过 | 未通过：8 像素 last 不同，T max 2.2177e-5 | 精确一致 |

主视角完整 320×178 的 FPGA RGB 最大/平均绝对误差分别 **1.6913e-5 / 1.2442e-7**，相对于同输入官方渲染的裁剪 RGB PSNR **134.78 dB**、SSIM **1.0**、LPIPS(VGG) **2.71e-8**。这些是**部署误差**，不是与实拍照片对比的重建质量指标；图像很像也不覆盖 last 的严格失败。完整视角 10 的 FPGA RGB 最大误差 **1.3113e-6**，T 最大误差 **2.3842e-7**、last 全部一致，严格通过。完整质量结果及官方指标实现哈希见 [GPU 独立评估摘要](../../npu_3dgs/benchmarks/scene_quality.json)。

100k 的 last 边界已用同一像素单射线独立重放，排除漏 Tile 或漏命令；CUDA 浮点融合/`exp` 舍入组合在 T≈1e-4 阈值附近改变是否接受最后一项。只增加 CPU 二次型 FMA 仍未消除反例，未改数值门槛和官方输出。细节见[保留的诊断](diagnostics/README.md)。50k 和 640 分辨率的 T 门槛也仍标红；本轮没有用肉眼画质或 PSNR 替换严格验证。

## 复现、版本和限制

- [完整数据/Golden 清单](data/20260926T135717/manifest.json)、[首次校准](evidence/calibrate_20260926T140258/result.json)、[另外四组校准](evidence/calibrate_20260926T140613/result.json)、[四规模重复测试](evidence/measure_20260926T141742/result.json)、[第二完整视角重复测试](evidence/measure_20260926T142849/result.json)，各有原始计时 CSV、板端实际 readback、冻结源码和 SHA256。
- [版本对照表](../../npu_3dgs/benchmarks/scene_versions.csv)和[哈希登记](../../npu_3dgs/benchmarks/scene_registry.json)将 `calibrate` 单次与 `measure` 三次分行，绝不把旧 4 点 Tile 混入同一性能排名。三次重复只说明同输入短期稳定，P95/P99 只是三个值插值，不能代表尾延迟。后端按固定顺序分进程运行，并非随机交叉实验。
- 冻结渲染源码 SHA256 `d475988da75f4ba15b67bb707e3d508f8f3d1d0637bb486fc9168ea87383e340`；板上可执行文件 SHA256 `d92344a32c4a3a561d57d53d46673d44e7f3b51379ad0d6b311f192534ab2c0c`。先前 GSB1 BOOT 不变；全板时序未闭合、功耗未实测。不得把本次功能验证当作硬件时序签核或能效结论。
- 复跑按 [输入契约](CONTRACT.md)，先在已有云 GPU 执行 `prepare.py`，再在同板卡、GSB1 BOOT 下以 `FPGA_BOARD_PASSWORD` 环境变量运行 `run_board.py` 的 `--phase calibrate` / `--phase measure`。需参考旧报告确认 BOOT/SDK 版本；不要运行已隔离的直接 `/dev/mem` 写入测试。

下一步工程优化应对准每帧 1.18 亿候选的 CPU 求值及 1.39 亿字节级寄存器供数：先验证块传输的真实可行性和带宽，再把 `power/exp/alpha` 尽可能与有序合成放进同一 Tile 流水，避免在 ARM 展开数百万条 BLEND 命令。是否再接 NPU，要在同一完整帧、相同精度门槛下，把 NPU 提交、搬运、同步全部计入；本轮没有新的 NPU 大场景性能数据。
