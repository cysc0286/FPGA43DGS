# FLK1 后续优化与 NPU 接入判断

2026-09-27。针对用户关于“还能否改善、FLICKER 如何加速、NPU 是否有机会”的问题，核对当前源码、最终 HLS 报告、已冻结实板数据和 FLICKER 原文。本记录没有新增性能测量，没有更换 BOOT，也没有启用 NPU。

最新用户决定：先完善 CPU+FPGA，NPU 延后。以下 NPU 分析仅作后备，不启动相关编译或上板。当前 CPU 只读取已有排序结果并打包调度，投影/SH/Tile 分组/排序仍在离线 GPU；完整链路后续优先以板端 CPU 补齐这些前处理，再与 FPGA 协同测量。不能将未实现的 CPU 排序写成现状。

CPU 协同优化的后续候选包括：减少每帧参数重打包、评估跨 Tile 参数复用、按真实 Tile 候选量调整任务批次，以及在驱动确有支持时比较轮询/事件等待。每帧当前 CPU 准备约 280/251 ms，且主机轮询占约一个核；准备与 FPGA 工作已部分重叠，不能将减少的 CPU 时间直接当成相同幅度的帧延迟下降。数据驻留只能缓存视角无关参数或有明确失效规则的派生数据，不能用重复固定视角缓存冒充动态相机加速。改变排序/批次时仍须保持每个像素的贡献顺序。

## 已确认的起点

固定官方 train/iteration_7000，559,263 Gaussian，v0/v10，320×178。Dense 含 CPU 准备、传输、同步和回读为 1.419/1.328 s；同 FPGA 在 AABB 后再启用 CAT 的收益为 1.302/1.370 倍。主机上传约 63.612/58.831 ms，硬件处理区间约 1385.089/1263.683 ms，二者有重叠，不能相加。来源：[实板报告](VALIDATION.md)和[完整数据](../evidence/board_cat_summary_20260927/REPORT.md)。

当前统计没有逐级 stall/VRU busy/CTU 淘汰数量，不能从设备总体耗时唯一确定哪一级是瓶颈。Slice 99.80% 是布局占用，不是算术单元忙碌率。优先改善调度和数据复用，再考虑增加并行硬件。

## FLICKER 机制及本板边界

依据：[FLICKER §III–IV](https://arxiv.org/html/2603.01158v1)、本地 `papers/metadata/06_FLICKER_DATE2026.txt`。层次流程是 8×8 AABB 粗筛、4×4 mini-tile 代表像素贡献测试、通过掩码进入 FIFO、VRU 对保留项实际求值并按深度合成。Dense 测四角、Sparse 测两对角；代表像素测试是近似，可能漏掉其他像素的有效贡献。

矩形共享复用中间项；共享 opacity 的对数阈值，避免每个测试点完整计算 exp。CTU 与渲染重叠，FIFO 满时施加背压。本板保留了这些计算/顺序机制，但只用四个 VRU、II=8 时间复用 CTU 和全 FP16。混合精度 CTU、聚类选择性取数、完整模型准备仍未实现。Sparse 在本板几乎不再提速且质量变差，暂不替代 Dense。

## 代码核查发现的优化机会

1. `pipeline.cpp::split` 每次读到一个 Gaussian–Tile 记录都会从 conic 重建半径和形状，包括除法与开方。同一 Gaussian 跨 Tile 重复出现时，这些与 Tile 无关、与当前视角有关的结果重复计算。HLS `split_csynth.rpt` 的 Gaussian 循环非流水化，迭代 84–258 cycles，尚未含下游背压。可以评估将几何计算与子块分发拆开流水，或按每帧每 Gaussian 计算一次并复用。后者涉及缓存/接口和前处理成本，须单独比较，不能把成本移出计时冒充提速。
2. `render_lane` 严格执行载入 16 像素状态→`evaluate_mini`→写回，再开始下一 Gaussian。局部像素循环 II=1 不能消除每次调用的填充/排空成本。同一像素的 alpha 合成依赖上一贡献，不能靠取消依赖检查或乱序执行换吞吐。后续可在独立 mini-tile 状态之间交错调度，保持每个像素内部深度顺序；具体速度和面积须综合及实板验证。
3. `framed_ctu.cpp::prepare_frames` 在展开 sub-tile 后准备共享阈值，对多个 sub-tile 仍有重复。复用点需要与前端边界一起评估，不直接同时修改，以便保留归因。

下一次工程只选择 **split 前端模块**，先补可归因的输入等待/输出背压证据并建立不改数学顺序的独立候选。当前 64 B 输入、FP16 Golden、六模式和 DMA 所有权作为冻结基线。模块验收包括六模式 C/RTL、背压/边界、最终资源及时序、两完整视角 raw 回读、CPU/Dense/旧 FLK1 同范围对照。若新增计数或流水结构无法装入当前 Slice，保留失败候选并调整该模块；不跳去同时重写 VRU 或加 NPU。

## NPU 接入机会与评价范围

NPU 的候选价值是已有的并行乘加硬件，可能承接规则批量计算并释放 PL 资源；是否节省 LUT/DSP、是否更快，取决于真实替换了哪些模块和数据交接成本。本次只评估机会，原 FLICKER 基线继续不启用 NPU。

|接入位置|拟承担工作|可能收益|主要限制|
|---|---|---|---|
|前处理，优先评估|大批量坐标变换；编译支持且精度通过时再扩展投影协方差、SH 颜色的规则子图|补齐目前离线 GPU 承担的链路，减少 CPU 前处理负担；可能释放部分 FPGA 算术资源|小矩阵未必有效填满阵列，含非线性/不同方向；不能假定 SH/exp/协方差全部支持|
|筛选后分块求值，后续候选|保留 Gaussian 的局部像素二次型乘加，FPGA 保留 exp/alpha/顺序累积|可能直接缩短渲染计算|展开结果比参数大、密集计算浪费已剔除/提前结束项、NPU 与 FPGA 交接和反馈成本高|

首选分工候选为 NPU 批量前处理→CPU 可见性收尾/Tile 分组/排序→现有 FPGA FLICKER 渲染。它是对 FLICKER 阶段的异构映射扩展，不能冒充原论文配置。静态世界协方差等应离线预计算，不为利用率每帧重复计算。

**前处理加速不能直接与现有 1.419/1.328 s 相比**，因为这两个数字排除了前处理。NPU 前处理验收必须另建“CPU 完整前处理＋同一 FPGA”基线，从模型与相机开始计时。即使下一帧前处理与当前帧渲染能重叠，也不意味着当前帧延迟自动变成两阶段最大值；需要区分单帧延迟、跨帧吞吐和排序/内存同步约束。

历史小批量 NPU 几何结果为 512 点 compact19 1.083913 ms，对优化 CPU 0.093379 ms，约慢 11.61 倍。证据为 [ROUND_20260926.md](../../../npu_3dgs/benchmarks/ROUND_20260926.md)。这是旧小批量、旧精度补偿路径的负结果，不能外推十万点，也不能因放大 batch 就承诺转为正收益。

重新研究 NPU 时先使用实际全场景的分块工作量做编译和数值验收；记录布局转换、padding、准备、提交、NPU 执行、CPU fallback、交接与下游完整耗时。比较 CPU+FPGA 和 CPU+NPU+FPGA，同模型、同相机、同排序、同质量标准。当前 FLK1 位流未做 NPU 运算回归，原厂 AI 脉宽限制仍在；共享内存可达性、完成同步和真实并行均须重新验证，不能沿用旧 SDK 初始化成功作为证明。

收益门槛是：端到端更快，或以明确的性能/质量代价降低实际 PL 资源或实测能耗。若只是 NPU kernel 更快而总时延更长，则保留负结果，不纳入主路径。不预测未经测量的 FPS、功耗或 NPU 利用率。
