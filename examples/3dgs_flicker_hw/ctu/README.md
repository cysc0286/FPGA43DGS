# FLICKER 独立 CTU（尚未接板端渲染）

直接依据 FLICKER §III-B Algorithm 1、§IV-C 的两个像素矩形处理路径和掩码合并编写。这里实现全 FP16 消融分支；没有把未经说明的 FP8 格式当作作者实现。

流程为共享 `ln(255*opacity)`、请求展开、两个矩形的共享二次型运算、掩码合并，级间为深度 16 的 FIFO。Dense 每个 8×8 sub-tile 需要两个请求，每个请求计算两个矩形；Sparse 用一个请求，两个矩形分别收集四个 mini-tile 的左上/右下 leader。所有阶段的 HLS 排程 II=1；这不代表上板频率或完整渲染吞吐已达到论文结果。

每个输入是一个已经过上游处理、按深度排序的 Gaussian/sub-tile 对，64 字节。前 9 个 FP16 特征沿用完整渲染核。附加字段：origin x/y 为 bit 144/160 起的两个 uint16；宽、高分别 bit 176/181 起的 5 bit，有效范围 1..8；bit 186 为上游 spiky 标志；bit 192 起的 32 bit 原始序号。输出保留全部输入字段，bit 224..227 增加四个 mini-tile 的掩码，顺序为左上、右上、左下、右下。即便 mask=0，也输出该记录用于后级核对序号；实际跳过渲染循环要在后续集成完成。

模式：0 旁路，1 Dense，2 Sparse，3 Smooth-Focused，4 Spiky-Focused。后两者只消费上游的 shape 标志；不能据此宣称已实现 FPGA 分类/投影。

`build.ps1` 完成 C 仿真、综合和 C/RTL 对比。首轮为 120 组输入 × 5 模式，加空输入；涵盖已知可分析的角点、稀疏漏筛、边缘裁剪、属性和序号保持。`evidence/ctu_fp16_srl_20260927T005305` 保留快照。真实高斯测试用 `prepare_real.py` 和 `real.tcl`，不会以几何图形的少量掩码通过替代真实场景或整帧质量测试。

SRL 调整解决本 FPGA 上浅而宽 FIFO 的 BRAM 浪费，代价是增加 528 LUT。两版功能 C/RTL 均通过。这是平台资源映射消融，不是论文的算法贡献；目前没有布线时序、板端延迟或功耗。

真实属性进一步验证已完成：768 个高斯、2,560 个有效 sub-tile 输入 × 5 模式 C/RTL 一致。`run_stalls.py` 在输出长时间暂停、上游间歇供数、六次空调用与连续模式切换下，12,800 条输出逐位保持一致；五次实证上游在下游暂停期间停止前进，恢复后无丢失。证据为 `evidence/ctu_stalls_20260927T010148`，不是物理 FPGA 结果。

`evidence/ctu_real/mask_analysis.json` 单独用 FP64 的 alpha 阈值分析编码后的 FP16 属性。这个有限子集上，硬件掩码与相同 leader 规则一致；Dense/Sparse/Smooth-Focused/Spiky-Focused 保留 1370/1292/1353/1309 个 mini-tile 对（旁路 9216 个）。它们分别漏掉 17/188/59/146 个潜在有效像素项（总共 16436 个，尚未计入 T 与提前终止）。这些数值说明筛选的取舍，不能当成完整场景画质或加速比。

仍未完成：8×8 AABB 的上游真实筛除、与 VRU 合并并实际缩短循环、完整整帧消融、FP16→FP8 CTU、投影/排序/聚类/模型准备。独立 CTU 的存在不等于这些任务完成。

工具问题单独保留：Vivado HLS 2018.3 的 IP catalog 导出用日期 `2609270049` 作为有符号整数 revision，首轮导出溢出，但 C/RTL 已通过。当前按渲染基线直接使用生成的 RTL，不改电脑时间，不把 IP 打包失败写成 RTL 失败或反之。
