# 历史资源预研（CPU链实现之前）

本文件保留当时的可行性判断；当前执行路线与实测状态以 README.md 和 VALIDATION.md 为准。

# 视频到高斯场景：后续部署研究范围

2026-09-28。用户要求将现有成果封装为独立“3DGS 渲染”，后续研究已有视频抽帧、重建高斯场景、再生成指定视角图像。本目录记录方案与资源依据，**当前没有完成视频重建或板端训练**。当前渲染交付包为 [3DGS Renderer v1](../../releases/3dgs_renderer_v1_20260928/README.md)。原 FLICKER 渲染实现、源码、BOOT 和历史实验保持冻结，不把它改名为重建系统。

工作假设：普通 RGB 视频、主体静态、相机有平移及视角覆盖，允许离线处理；动态物体/4D重建、在线SLAM、NPU和下游检测导航暂不纳入。该假设用于本轮可行性判断，不是对尚未提供视频内容的断言。

## 目标链路与接口

```text
已有视频
  → 解码、选取清晰且有重叠/视差的关键帧
  → 相机标定/去畸变、位姿估计、初始三维点
  → 有数量和内存预算的高斯初始化与迭代优化
  → Gaussian PLY＋目标相机位姿/内参
  → 已封装的 CPU＋FPGA 渲染器
  → 指定视角图像
```

“特定位置”须补齐朝向和相机内参，并使用重建坐标系；单目模型若要对应实际米制位置，还需尺度/坐标对齐。目标视角宜位于视频有充分覆盖的区域；降低质量要求不能恢复完全未观察到的真实表面。单纯原地旋转、强模糊、缺少纹理或大量运动主体都会影响重建，不能把所有错误归为算力不足。

未来上游只需对接 [渲染输入合同](../../releases/3dgs_renderer_v1_20260928/INTERFACE.md)。当前 v1 是 SH3、62 浮点字段的严格 GraphDECO PLY，而非任意XYZ/RGB点云。SH0/SH1模型需要转换适配；零填高阶系数可以兼容格式，但不节省旧解析器的存储或运算。模型精度/ABI变更独立版本化。

## 论文与路线选择

|依据|解决的问题|代码与适用性|本阶段定位|
|---|---|---|---|
|Structure-from-Motion Revisited，CVPR 2016 / COLMAP|由多帧恢复相机位姿和稀疏三维结构|[论文](https://openaccess.thecvf.com/content_cvpr_2016/html/Schonberger_Structure-From-Motion_Revisited_CVPR_2016_paper.html)、[代码](https://github.com/colmap/colmap)；支持CPU特征路径，需实测ARM编译/内存|视频几何前端候选|
|3D Gaussian Splatting for Real-Time Radiance Field Rendering，SIGGRAPH 2023|位姿/图像/初始点→拟合高斯→新视角渲染|[作者页](https://repo-sam.inria.fr/fungraph/3d-gaussian-splatting/)、[代码](https://github.com/graphdeco-inria/gaussian-splatting)；原版优化器依赖CUDA|完整功能流程和数值基准|
|Taming 3DGS: High-Quality Radiance Fields with Limited Resources，SIGGRAPH Asia 2024|控制增密至指定Gaussian预算，并优化反向与属性更新|[作者页](https://humansensinglab.github.io/taming-3dgs/)、[代码](https://github.com/humansensinglab/taming-3dgs)；公开`--budget`/`--mode final_count`，作者测试为GPU|低资源重建的优先方法候选；不是现成FPGA工程|
|Gaussian Splatting SLAM / MonoGS，CVPR 2024|RGB视频的连续相机跟踪和高斯建图|[作者页](https://rmurai.co.uk/projects/GaussianSplattingSLAM/)、[代码](https://github.com/muskie82/MonoGS)；公开实现使用CUDA，作者实验RTX4090|证明视频链路可行；离线首版无需引入完整在线SLAM|
|SplaTAM，CVPR 2024|RGB-D相机跟踪、建图和新视角渲染|[代码](https://github.com/spla-tam/SplaTAM)；RGB-D包含深度输入|普通RGB视频不能直接替代为该输入，暂不选|
|LightGaussian，NeurIPS 2024|贡献剪枝、恢复优化、SH降阶和量化|[作者页](https://lightgaussian.github.io/)、[代码](https://github.com/VITA-Group/LightGaussian)|模型压缩备选；训练后压缩不能自动解决此前训练峰值|

建议采用一个明确组合：原始3DGS定义重建与输出语义，COLMAP提供离线位姿和初始点，Taming的预算控制作为资源优化候选，冻结FLICKER作为渲染后端。不是同时复现上表六条路线。Taming项目页有Equation 2勘误，后续实施须以更正公式和锁定代码为准；本轮只是路线核对，尚未完成其逐公式移植。

[COLMAP官方教程](https://colmap.github.io/tutorial.html)明确建议视频降采样、足够视角重叠及相机平移，并提供适合视频顺序的Sequential Matching。原始3DGS仓库也提供图像到COLMAP数据的转换脚本和`--no_gpu`，但该选项作用于COLMAP准备阶段，**不表示3DGS CUDA优化器变成了CPU训练**。

## 当前资源是否支持

本轮SSH实查：[环境记录](../3dgs_flicker_hw/evidence/renderer_package_20260928/environment.txt)。4核Cortex-A53，Linux可见内存993MiB、检查时可用747MiB，无swap，根分区余15GiB。已找到`ffmpeg`，`colmap`不在PATH。Linux可见容量不是整板所有PS/PL保留DDR容量的总和；未把保留地址区假设为普通训练内存。

现有FPGA物理报告：LUT78.08%、FF62.57%、DSP65%、BRAM75.66%、Slice99.99%。当前位流仅有前向筛选/求值/合成，没有可调用的训练反向、损失梯度和优化器。现有SDK提供传输，不等同于训练后端。原厂AI时钟脉宽违例及既有I/O/CDC限制继续保留。

判断：已有资源足够继续验证抽帧与有界小模型方案，但不能原样部署主流CUDA工程，更不能据此承诺全板训练速度或质量。首先要验证ARM的位姿求解与优化器能否在预算内运行。将环节串行执行、逐帧读取、释放中间结果，可以降低峰值；整条链路不要求所有环节同时占据FPGA。

### 内存估算，不是实测峰值

以FP32参数、梯度、Adam一阶/二阶状态四份数组计，SH3每Gaussian有59个待优化数值，SH0有14个：`内存=N×参数数×4字节×4份`。不含图像、相机/SfM数据、Tile列表、前后向中间量、临时分配、运行时和硬件缓冲。

|Gaussian预算|SH3四份参数数组|SH0四份参数数组|
|---:|---:|---:|
|20,000|18.01MiB|4.27MiB|
|50,000|45.01MiB|10.68MiB|
|100,000|90.03MiB|21.36MiB|
|当前559,263|503.49MiB|119.47MiB|

公式与机器可读值见 [resource_estimates.json](resource_estimates.json)。这说明“先控制Gaussian预算与颜色复杂度”有明显的内存意义，但不能把10.68MiB写成整个5万点训练只需的内存。图像和光栅化临时内存可能占主要部分。

## 如何用质量换资源

|调整|主要减少什么|代价及限制|
|---|---|---|
|从20k/50k/100k预算逐档测试，限制增密峰值|模型、梯度、优化器状态及多数计算|细节/薄结构可能丢失；覆盖范围和贡献重要性比随机删点更重要|
|重建图像先用约320宽，再与640宽比较|图像、光栅化和梯度工作量|高频纹理变模糊；位姿估计可保留更高分辨率，不能盲目一起降|
|SH3→SH0/SH1|参数量和颜色计算|反光、视角相关外观变差；需要新的紧凑格式/前端才能兑现全部收益|
|清晰关键帧、顺序匹配、小批图像读取|重复解码/匹配/训练与图像驻留|过度抽帧可能失去重叠和视差，导致几何失败|
|局部优化窗口、分阶段释放数据|峰值内存与每次迭代工作量|全局一致性可能下降；需保留可检测的重访/对齐误差|
|减少迭代并早停|处理时间|几何和外观可能欠拟合；以未参与优化的视角质量判断|
|降低FPGA并行VRU数量、复用算术单元|实际LUT/FF/DSP及布局压力|通常增加渲染耗时，未必损失数值质量；必须重综合和实板确认|
|收窄数值位宽或定点化|可能减少硬件面积与带宽|数值误差、溢出和质量风险；具体节省须看物理报告|

**输入点数/分辨率下降不会自动释放旧位流的Slice。** 当前占满的是电路布局。更小输入会让相同电路少工作，但电路还在。若只新增CPU软件阶段，可以先保留v1位流；若增加硬件反向模块，必须先做独立精简平台，评估移除未使用的厂商演示/视频/AI部分及减少并行单元。SDK初始化和DMA可能依赖厂商平台，不能直接删除AI命名模块就假设传输仍可用。

不以“把所有位宽都减半”作为首个改动，也不先牺牲相机位姿正确性。优先保留几何和视角覆盖，减少冗余点、高阶外观与过多训练帧。

## 可验证的后续顺序

1. **已有视频→帧与位姿。** 首个视频假设静态短片，先选20–60个清晰且有视差的关键帧；记录抽帧率、注册成功率、重投影误差、CPU耗时及峰值RSS。先判断几何是否成立，不能跳过位姿生成直接把每帧像素写成同一坐标系的Gaussian。
2. **位姿/图像→预算高斯模型。** 先建立可微CPU参考和小模型优化，确认梯度、损失与参数更新方向正确；比较20k/50k/100k、SH阶数和图像分辨率。目标是限制训练峰值并能收敛，不声称通过改启动参数就移植了CUDA反向。Taming候选单独冻结版本、预算和公式。
3. **模型→指定新视角图像。** 经格式适配调用冻结渲染包；选留出视角与真实帧比较PSNR/SSIM/LPIPS，记录空洞/漂浮物/局部误差。原46–48dB是相对官方渲染一致性，不能拿来当视频重建质量目标。
4. **选择值得加速的阶段。** 以解码/位姿/优化/渲染各段耗时、峰值内存和质量做消融，再决定CPU并行、硬件精简或反向加速。小模型能离线完成不等于可以实时跟随视频。

首轮资源目标建议把CPU工作集约束在512MiB以内并单列tmpfs/共享缓冲，给系统留余量；这是待实验的预算，不是已证明容量。质量候选可先限定相对同视频较大预算参考PSNR下降不超过2dB、SSIM下降不超过0.03，并检查几何/空洞；这是建议门槛，需在该视频正式对比前冻结。多档预算保留完整速度–内存–质量曲线，不仅展示最好一帧。

本轮没有用户视频输入，也未运行位姿或训练实验。因此目前结论是“路线成立，已有渲染模块可复用，板端全链需受限移植并实测”，不是“视频重建已部署”。
