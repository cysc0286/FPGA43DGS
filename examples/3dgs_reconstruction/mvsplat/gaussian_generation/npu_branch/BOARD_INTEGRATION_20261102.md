## 结论与边界

结果是一次有限实验，不是多场景性能统计。CPU、NPU、重叠三组各一次；没有足够样本报告 P95/P99。当前代码未提交、未推送。

## 实际发现与修复

最初资格检查还依赖板端没有安装的 Pillow，已改为已有 OpenCV 并验证 RGB/BGR 顺序。
随后复现了更关键的设备共存问题：两个独立进程打开同一 ICraft 设备，各自的 SDK 分配器使用同一片 PL DDR。

| 实验 | 结果 | 可支持的判断 |
|---|---|---|
| NPU 单独运行 | 输出有限、两次逐位一致；严格 tensor 门槛失败 | 稳定的精度偏差仍存在 |
| 先 NPU、后渲染器 | NPU 原本稳定，渲染器初始化后超时/非有限 | 设备初始化顺序会干扰会话 |
| 先渲染器、后 NPU，无地址预留 | 初始化后稳定，实际 FPGA 渲染后输出改变 | 单改启动顺序不够 |
| 同一候选库，先渲染器＋预留 64 MiB | FPGA 前后 oracle 一致，完整 Gaussian 重复一致 | 地址隔离在本实验中有效 |

64 MiB 是 NPU 分配器中的设备地址预留，不向该区间写数据，不额外占用 64 MiB ARM RAM。
日志显示预留 `[4096, 67112960)`，NPU 其余分配从 67112960 开始。该对照强烈支持 PL DDR 分配重叠的判断；没有声称修复了所有 SDK 权重预检问题。

`initialize/session.py` 与连续入口均改成先打开渲染器，再保留 NPU，退出时先关 NPU、后关渲染器。
`worker_environment()` 默认 `MGS_NPU_DDR_GUARD_MIB=64`；worker 核对新桥接库的实际分配记录，老库不支持时明确拒绝，不悄悄忽略隔离。
渲染 wrapper 在提交前按高斯数、batch、Tile header 与输出估计单次工作区上界，超过预留拒绝。该检查不证明 SDK 长时间反复扩容不会累积分配；当前证据限 32768 点、128×128 和本轮有限视角，扩大场景或长期连续刷新仍须专门做地址分配压力验收。

## 数值、画质与重复性

旧 tensor 门槛 `rtol=2e-3, atol=2e-4` 仍然失败：backbone max abs `0.0400121808`、RMSE `0.00519463064`。没有把它改成通过。
实际采用额外的、资产绑定的原生图像验收：输出有限且重复稳定、三个留出视角比较、FPGA 渲染后再推理与 oracle。`qualification_v3/acceptance.json` 全部通过，完整 NPU 高斯重复哈希相同。

| 留出帧 | NPU 对 CPU 图像 PSNR / SSIM | NPU 对真值 PSNR / SSIM |
|---|---|---|
| 7 | 55.329 dB / 0.999310 | 20.115 dB / 0.802044 |
| 15 | 56.396 dB / 0.999302 | 20.218 dB / 0.834233 |
| 22 | 54.722 dB / 0.999282 | 24.182 dB / 0.844241 |

相对真值的 PSNR 没有下降，SSIM 最大降幅约 0.0000305。这个结论仅针对上述固定输入。
重新从视频解码、估计位姿的两条完整链，首帧 NPU 对 CPU 为 50.475 dB / 0.998682，最大单通道像素误差 40/255、平均绝对误差约 0.001085（归一化）。整体接近，但局部最大误差不为零。
原生后端仍把网络 SH4 适配为 SH3；已有导出校验继续保留，该变化两条路径一致，不是本次 NPU 新引入。
图像可辨认室内结构，有 128×128 固有的模糊、边缘空洞和新视角遮挡问题；不能因 CPU/NPU 接近就称重建质量很高。

## 全链计时

统一边界为视频已闭合、交给系统的 `VIDEO_COMPLETE` → 第 7 帧新视角 `FRAME_COMPLETE`。预热、网页用户停留不计入性能；不把整个监控进程的墙钟时间当首帧。

| 路径 | 网络前向 | 视频结束→首帧 | 进程树采样峰值 RSS / 最少 MemAvailable |
|---|---:|---:|---:|
| CPU＋FPGA，4 线程串行 | 15.739 s | 29.317 s | 611.60 / 294.19 MiB |
| NPU backbone＋CPU＋FPGA，4 线程串行 | 15.058 s | 28.509 s | 611.02 / 256.95 MiB |
| NPU backbone＋CPU＋FPGA，3 线程推理与位姿重叠、内存交付 | 16.038 s | 24.356 s | 623.12 / 228.05 MiB |

串行 NPU 较 CPU 节省 0.809 s（2.76%）。重叠候选较串行 CPU 节省 4.961 s（16.92%，1.204×），但它同时改变了调度、线程数和内存交付，不能把全部收益归因 NPU。
尚未做 CPU 同调度对照，不能从第三行推出“NPU 相对同调度 CPU 快 16.92%”。本轮目标是确认真实 NPU 链路与现有优化可以一起工作。

同一个 prepared input 的资格检查中，CPU 前向 15.705 s、NPU 前向 13.632 s，重复 NPU 13.782 s。这个阶段差异大于完整视频那次，反映首次算子/缓存与运行差异，不能把两种统计混用。
预热仅记录：CPU 44.613 s、串行 NPU 54.703 s、重叠 NPU 54.801 s；视频前加载了权重、设备和 SDK，不等于每一个推理算子都已执行过。

重叠关键路径：上下文就绪 5.690 s、首目标位姿就绪 6.916 s、全部位姿完成 9.259 s、推理结束 22.708 s、首帧 24.356 s；位姿与推理实际重叠 3.568 s。
输入解码 3.483 s，上下文 SIFT 1.552 s、匹配 0.399 s、位姿 0.148 s；目标 7 的 SIFT/匹配/PnP 合计 1.127 s。
3 线程前向本身稍慢，但首帧无需等待后续导出审计，整体更快。首帧之后的 PLY/回读验证仍完成。

## NPU 调用成本

资格检查中的一次完整 backbone 调用（不是全网，不是纯硬件周期）：

- 打包 2.193 ms，等待 worker 16.548 ms，解包 5.816 ms，总 24.557 ms。
- SDK 内：传入 0.186 ms、forward 提交 1.165 ms、等待 0.006 ms、SFB 输出转换 11.234 ms；SDK 总计 12.591 ms。
- 这些嵌套计时不可相加重复计算；SDK `forward` 的返回语义不等于裸 NPU 执行周期。
- 逻辑输入 393216 B、输出 1048576 B，合计 1.375 MiB；不是 DDR/DMA 总流量。
- 当前只用一个 retained backbone 会话，其余深度、注意力、重采样、细化、高斯适配仍在 CPU。

通过本机 SSH loopback 隧道 `127.0.0.1:18434` → 板端 `127.0.0.1:8080`。网页服务留在 loopback，POST 和场景信息需要当前会话 token。

| 指标 | 六次范围 | 六次均值 |

| 板端相机请求→完整 RGB | 50.59–53.09 ms | 51.445 ms |

浏览器时间含当前 SSH 隧道、PNG 和显示；不是任意网络保证。渲染耗时包含 CPU 投影/排序及 FPGA 服务，不是 FPGA 内核单独耗时。
