## 1. 输入、计时与版本边界

## 2. 新发现：重复同一输入掩盖了上一请求结果

新增 `input_switch_probe.py`，分别对两个真实 NPU 分区执行 A,A,B,B,A,A,B,B；A 为原固定 oracle，B 为全零输入。保存每次输入/输出 hash、结果差值与完整调用成本，不以 CPU 推理替代 NPU。

原桥接库在 backbone 的 B 首次、A 再次首次、B 再次首次，均返回**上一组输入的精确输出 hash**；与当前输入稳定结果最大差值为 5.03418。depth_head 在这组测试中没有此现象。仅 A,A 重复检查会放过这一故障。

完整合成输入预热也触发了它：预热后第一次 backbone oracle 的 RMSE 为 0.8640，下一次恢复为 0.005195，READY 被拒绝。相比正常 TF32 量化误差，这是不同问题。没有把该次失败的短调用当作加速。

| 控制实验 | 板端结果 | 评价 |
|---|---|---|
| 每次重新创建输入 Tensor | 仍不通过 A/B 切换 | 输入对象身份重建不足以解决 |
| 每次重新 session.apply | 仍不通过 A/B 切换 | 不是可依赖的会话恢复方案 |
| 强制输出 setReady(false) 再等待 | 仍不通过 A/B 切换 | 未修复同步/回读根因 |
| backbone 同一输入执行两次 | 通过本轮 A/B 切换、三视角及两次完整视频 | 可审计的规避办法，SDK 根因仍未关闭 |

底层诊断依据为本板 SDK 的 `Tensor::waitForReady`、`setReady`、`Session::forward` 接口；没有臆造寄存器协议或进行设备直接寄存器写入。不能仅凭现象断言是某一层缓存或 DMA 硬件损坏。

### 正式门槛与规避策略

`readiness.py` 在交错分区 oracle 检查后，增加 B,B,A,A 输入切换；回到 A 的第一次输出就必须等于已保存 A hash。旧 receipt 不能绕过此检查；失败不能发布 READY。

显式设置 `MGS_NPU_SETTLE_BACKBONE=1` 时，worker 对 backbone 执行两次完整 SDK forward，丢弃第一次，记录 `sdk_execution_passes=2` 并累加两次分阶段耗时。depth_head 仍为一次。此策略写入运行身份并绑定新 receipt；不是隐藏重试、不是设备零拷贝，也不是 SDK 根因修复。

修正后有/无完整前向预热的两次视频产生**相同 Gaussian NPZ hash**：
`08e4f4361940d7ecca066508f3782ca6539dad69be36ce9f4ff54142487fa009`。
它们与旧的一次执行候选高斯 hash 不同。因此旧 23.634 s 只能保留为当次固定视频的历史记录，不能作为修正后通用 NPU 路径的成绩。

## 3. 完整视频：最终可用数据

| 实现 | 视频结束→完整首帧 | 完整网络前向 | 预热，仅记录 |
|---|---:|---:|---:|
| CPU 3 线程＋准备 1 线程＋FPGA | 24.5118 s | 16.4141 s | 42.034 s |
| 修正 NPU 双分区，同样调度 | 24.3530 s | 16.0186 s | 57.762 s |
| 修正双分区＋合成输入完整前向预热 | 23.9331 s | 14.5080 s | 72.964 s |

最后一行相对第二行少 0.41985 s（1.72%），相对 CPU 少 0.57867 s（2.36%）；各一次，不给 P95、P99 或稳定加速结论。预热候选完整推理少约 1.51 s，但其他关键路径开销抵消了大部分；不能只报网络阶段收益。

完整预热使用固定常数图像、固定相机基线和原权重，在 READY 前执行一次前向，丢弃所有输出，再对实际 worker 复验。没有提前处理输入视频、训练权重、复用真实视频高斯或把真实输入工作藏进预热。
该选项为 `--warm-kernels`，默认关闭；本轮不足以决定改成默认。首次不带输入切换规避的预热失败记录完整保留。

### 同固定输入的网络阶段对照

新的两次执行策略加输入切换门槛下，四线程资格程序中 CPU 前向 15.8471 s，NPU 前向 13.3988 / 13.2529 s。三次程序顺序为 CPU、NPU、NPU 重复，CPU 首次使用与缓存效应未对称消除；不把全部差值归因于 NPU。

更早的三线程同进程交替诊断（尚未加入两次执行规避）得到 CPU 均值 14.4700 s、backbone 单分区 13.2101 s、双分区 12.8751 s。新增 depth_head 两轮分别省 0.2510 / 0.4190 s，均值 0.3350 s。
它是固定输入的诊断证据，不覆盖输入切换问题，不用于替代上表的修正后整链成绩。

## 6. 布局与数据调用优化

`artifacts.py` 增加按 8 行、16 通道分块的直接布局复制；逐元素结果与原布局相同，覆盖非连续数组、通道尾块。runtime 仅对至少 4 MiB 输入启用，小张量保留直接复制。

| 分区输入整理 | 原连续临时量 | 直接复制 | 分块复制 |
|---|---:|---:|---:|
| proj_feature | 647.58 ms | 634.37 ms | 211.38 ms |
| to_disparity | 162.09 ms | 158.00 ms | 53.76 ms |
| backbone_cnn | 2.215 ms | 2.043 ms | 3.502 ms |

这是板端五次交替测量的布局整理中位数，不是 NPU 全图、DMA 或整链收益。depth_head 分块同样更慢，因此不启用。当前接受的两个小边界没有因大张量分块而获益。

worker 继续分别记录输入整理、SDK 写入、提交、等待、输出转换和完整调用。修正后固定输入一次 backbone 完整调用约 40.3 ms（包含两次 SDK），depth_head 约 32.6 ms。七分区 79.5 MiB 是逻辑边界之和；实际接受两分区为 3.375 MiB 逻辑边界，额外 SDK 执行还有设备内部成本。均不是实测 DDR 流量，不能称零拷贝。
