# NPU 回板核验与参赛部署主线（2026-11-02）

## 结论与部署边界

电脑以太网 1 Gbps、192.168.126.49:22 与固定主机密钥 SSH 均可达。
当前源码的新桥接库在默认字符串输出路径下，完成了公开短片 → CPU 位姿 →
CPU＋NPU 高斯生成 → 冻结 FPGA 渲染 → 网页确认视角的真实板端闭环。
128×128、32768 高斯，视频结束到首帧 **22.393 秒**。同调度 CPU 对照
23.863 秒；旧正式桥接库 NPU 为 22.138 秒。各一次，不据此证明小幅变化稳定，20 秒尚未达到。

用户本轮明确：参赛首先需要合理、可解释、可以演示的 NPU 部署，再在这条链路上优化。
因此保留 `backbone_cnn + depth_head` 的正式分工，不为了提高子图数量接入错误输出，
也不把边界微基准作为系统成果。严格 TF32 张量门槛仍失败；部署采用已有且本轮重验的
三留出视角图像政策、资产绑定和每次启动的有限值/重复性/输入切换检查。

`DIRECT_SFB=1` 虽通过一轮固定输入三视角资格，却在完整视频入口的 READY 前出现
backbone 输入切换不一致。因此继续默认关闭，不能升级为正式优化。
新增 Gaussian head 的八个编译图、16 个诊断配置也未通过全部数值与状态检查。

## 参赛链路怎样部署

```text
initialize：视频前加载固定权重、编译图与运行环境，预热并检查；通过后发布 READY
video_input：接收完成的视频，记录 VIDEO_COMPLETE，解码并选择上下文/目标帧
pose_estimation / CPU：特征、匹配、相机位姿与目标视角；与推理按既有线程预算重叠
gaussian_generation：NPU 执行 backbone_cnn、depth_head；CPU 执行其余网络与几何
rendering：CPU 投影/分组/排序，冻结四路 FPGA 求值与合成；网页确认相机后返回 PNG
```

这是预训练 MVSplat 的前向重建，没有逐场景反向训练。两个上下文帧为 0/29，
三个留出目标为 7/15/22；30 帧并非全部送进网络。一次视频测的是第 7 帧目标位姿的首帧，
不是全段视频完整空间覆盖。高斯已准备后，交互换视角调用渲染器，NPU 不在此时重复生成高斯。
代价体重采样、注意力、细化网络和 Gaussian head 仍主要在 CPU，不能称全网 NPU。

代码继续保留四业务模块，`initialize` 管生命周期；本轮没有新增第五个业务模块、改 BOOT 或 RTL。

## 完整视频与网页核验

同一公开 `nyu_snippet_curl.mp4`、固定权重、128×128、32768 点；合成输入完整预热后
才接收真实视频，CPU 推理 3 线程、准备 1 线程。计时使用单调时钟，
`VIDEO_COMPLETE → FRAME_COMPLETE`；预热只记录。未禁用首帧目标 PnP、适配检查或图像检查。

| 路径 | 视频结束→首帧 | 完整网络前向 | 结果 |
|---|---:|---:|---|
| CPU＋冻结 FPGA | 23.863 s | 15.155 s | 完成 |
| 旧正式库，双子图 NPU＋FPGA | 22.138 s | 13.873 s | 完成 |
| 新库默认输出，双子图 NPU＋FPGA | 22.393 s | 13.946 s | 完成 |
| 新库直接输出 | 无有效成绩 | 未开始真实视频推理 | READY 前输入切换失败 |

三次成功运行的预热分别 61.018/68.297/74.889 秒，只作运行记录。
CPU 与两条成功 NPU 路径的输入、目标相机一致；两条 NPU 首帧 PPM SHA256 完全相同。
本轮首帧 NPU 相对 CPU：PSNR **55.3205 dB**、SSIM **0.999239**；
相对留出实拍：**19.4499 dB / 0.804071**。图像接近 CPU，但原重建仍有模糊和遮挡问题。

新默认路径生成的场景已装入常驻网页服务，`/scene` 实际报告 NPU 已执行和 FPGA 后端。
6 次带请求编号的 HTTP 渲染：板端 **40.70–46.59 ms**，电脑发请求到收到 PNG
**53.61–76.76 ms**；三种视角各两次，相同视角 PNG hash 一致，不同视角各异。
这些 HTTP 时间不含浏览器显示。另用真实浏览器验证滑块选择与点击确认：
选择时显示“待确认”且上一视角编号保持，确认后返回编号 1、8° 新视角，
板端 **42.51 ms**、请求到显示 **65.0 ms**。网页截图已保存，本轮没有修改前端布局。

## 新库的固定输入资格与拷贝候选

独立 ARM g++ 链接通过。先用旧正式库对照，再分别测试新库的字符串和直接输出。
每轮固定已准备输入，CPU/NPU 前向、三个留出视角原生 FPGA、再次推理与 oracle 复验。

| 库/输出路径 | CPU 前向 | NPU 前向 / 重复 | 图像与重复性 |
|---|---:|---:|---|
| 旧正式库 | 16.798 s | 14.049 / 13.822 s | 通过 |
| 新库字符串 | 16.441 s | 13.348 / 13.306 s | 通过 |
| 新库直接输出 | 16.506 s | 13.340 / 13.631 s | 通过，但随后视频启动失败 |

三视角相对 CPU 分别 54.3688/55.4013/53.8831 dB，SSIM
0.999227/0.999154/0.999147；三轮生成的高斯 hash 及三张对比 PNG 完全一致。
张量严格门槛均未通过，不能把图像资格改写成逐元素正确。

新库单轮实际模型调用中，两子图合计由 72.096 ms 到 60.673 ms；
SDK 输出转换合计由 35.402 ms 到 24.653 ms。完整网络变化没有稳定优势，
这些不是重复配对统计。尤其直接输出在不同启动流程失败，**不作为可发布收益**。

说明该次异常不能单独归咎于直接拷贝；但也不能据此证明直接拷贝可靠。

## 资源、代码修复与原始证据

rootfs 仅剩约 1.9 MiB，所有新实板写入位于本轮专属 `/dev/shm`，没有清理队友或历史目录。
ARM 的 SDK 与渲染地址隔离保留 64 MiB。成功视频 CPU/旧 NPU/新默认 NPU 的采样
进程树 RSS 峰值为 597.75/586.39/585.70 MiB，最低 MemAvailable
166.59/161.90/158.88 MiB。共享页会重复计入 RSS，tmpfs/保留证据量也影响可用内存，
不把全部差异归因于算法。三轮独立资格 RSS 为 673.51/597.84/644.63 MiB。

FPGA/BOOT hash 已核对，没有重综合。历史资源：LUT77.94%、FF62.58%、
Slice99.84%、BRAM36等效82.45%、DSP63%，200 MHz；继承时序/CDC 限制仍保留。
NPU 活跃率、实际 DDR 流量和功耗未测。没有本轮资源优化或新 RTL 加速结论。

- `head_probe.py` 增加同会话输出路径配对、每标签哈希/有限值检查及运行标志记录。
- `readiness.py` 补上“B 与 A 必须不同”，避免永久缓存原 oracle 冒充输入切换成功；
  新默认路径视频实测通过加强后的检查。
- `evaluate.py` 将 Pillow 限制在报告画布生成中，原生数值比较不再因缺 Pillow 中断；
  首次资格的缺依赖失败也保留，修复后重新完整运行，没有补造成功收据。
- CPU 回退、四模块和冻结渲染包保持可回退；直接输出默认关闭。

机器摘要见同目录 `NPU_HEAD_BOARD_SUMMARY_20261102.json`。
原始脚本、SDK stdout、每次输入/输出及 hash、三视角资格、失败记录、完整视频、网页请求和截图位于
`D:/ADProjects/FPGA for 3DGS/outputs/npu_head_board_20261102/`，不提交模型/场景大文件。
已完成的 RAM 测试目录在下载 tar.gz 并校验 SHA256 后才回收；当前网页场景保留供展示，重启会丢失。

`3afa189fc93fa3b09f75797fc4600710c6f0d91a6cd813786a348efa7967d9e1`；
