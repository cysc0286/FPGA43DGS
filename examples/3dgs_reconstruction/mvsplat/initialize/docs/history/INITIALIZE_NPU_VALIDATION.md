## 实现结果

1. 预热资源管理拆到 `initialize/session.py`，视频文件接收/准备拆到 `video_input/`，视频结束后的调度为 `warm_pipeline.py`。原冷入口和冻结渲染包保留。
2. 四事件合同落地，主计时 `VIDEO_COMPLETE→FRAME_COMPLETE`，包含首帧渲染。预热和视频输入不作为性能指标；预置文件交付不捏造采集时长。
3. 模型只加载一次。上下文对完成后主线程执行 Torch，准备工作线程继续目标 PnP，汇合成功后才能发布场景。默认 2+1 线程；仍保留串行消融。
4. 投影服务一次加载 Gaussian rows，复用相机变化；FPGA SDK 服务保留设备句柄。Tile 分组仍用冻结子程序，动态场景数据/工作区仍需准备；没有声称 FPGA 全场景缓存或零分配。
5. NPU 导出/编译/审计/驻留会话/缓冲/布局/任务序号/数值和图像核验/打包完成。7 分区均为实际 MVSplat 模块。未选层、跨视图注意力、代价体重采样、细化 UNet、Gaussian adapter 等仍在 CPU。
6. 板端执行器补了进程树内存及超时监控，断连保留原错误、不自动重跑。上次 warm v2 只取回 READY，随后 SSH 10054；没有首帧证据，原因未知。

## NPU 边界代价与优先级

本报告首版全部分区逻辑输入/输出为 **83,361,792 字节 = 79.5 MiB/前向**，相同大小用于首版逐分区可复用共享缓冲。后续 [部署 v2](NPU_DEPLOYMENT_V2.md) 将映射总容量降到 36.375 MiB，逻辑 I/O 仍为 79.5 MiB。它们都不是完整进程峰值，也不等于实测总线流量。upsampler 18 MiB、proj_feature 20 MiB、to_gaussians 30.875 MiB 占主要部分；不能只看卷积执行时间。

优先验收 backbone 与 to_gaussians 的独立完整场景候选，再按实际 `pack / SDK write / forward+wait / SFB conversion / unpack / total` 选择组合。共享映射避免逐算子建进程和重载会话，但 CPU 重排及 SDK 拷贝仍存在。进一步融合需要处理多消费者依赖，不能把中间张量简单省掉。

## 失败版本保留

- `mvsplat_npu_compile_20260929`：ICraft 输入 mean 长度须与通道数匹配；v2 又发现 scale 长度要求。改为逐通道显式数组，v3 全部编译/审计通过；未改网络。
- `mvsplat_npu_bridge_syntax_20260929`：`Context` 与 SDK 类型同名。改为 `MgsContext` 后 v2 通过。
- `warm_split_cpu_local_20260929`：错误地把两线程候选与四线程参考要求逐位一致。输入和相机相同，但 Gaussian 有微小浮点差异。补同线程冷参考后 v2 完全一致；旧失败记录保留，并加入配置一致性检查，未降低精确匹配要求。
- 一次模块测试命令把 `modules` 错当顶层测试包，触发相对导入错误；改为项目既有 `tests` 入口，19 项通过。不是改源代码掩盖接口失败。
