# 双视频入口、ARM 预处理及 NPU 增量验收（2026-11-03）

## 用户确定的边界

“FPGA 预处理”指在开发板上完成，本轮使用板端 ARM，不新增 PL 视频解码、裁剪或缩放模块。原有四业务模块保持不变：`video_input → pose_estimation → gaussian_generation → rendering`；`initialize` 负责预热、状态、单实例与内存保护。

两个网页入口共用同一个服务和后续链路，不开两个 NPU 或 FPGA 所有者：

- `/capture`：开发板 USB 摄像头。沿用既有采集代码，点击开始后录制；点击结束后关闭视频、验证并自动提交重建。
- `/upload`：上位机浏览器选择电脑上的视频文件，以原始字节流上传到板端；板端接收、校验、原子发布，再提交同一重建入口。浏览器不能直接让板端读取电脑本地路径。
- 两者都由 ARM 解码、按当前模型要求缩放和中心裁剪；MVSplat 网络输入仍为 128×128。非规格输入不是在电脑上先转成模型尺寸。

USB 入口继续使用已有相机标定。电脑上传视频不能继承 USB 相机标定，使用显式 `--upload-focal-ratio` 参数（当前默认 0.525）；它是估计内参，不是素材已标定的证明。页面展示原始尺寸及预处理方式。中心裁剪会舍弃边缘，不能称为保留完整原始视场。

## 代码与交接

`video_input/upload.py` 只负责有界接收和视频验证，不依赖 USB 相机或模型。默认限制 256 MiB、1–120 秒、最短边至少 64、单边不超过 4096、总像素不超过 3840×2160、帧率不超过 120；保留至少 64 MiB 存储余量。超限应返回明确错误，不保证任意格式、损坏文件和无限尺寸视频均能运行。

接收过程以分块写入自有目录的 `video.partial`，不把整段视频放入 RAM；检查实际解码帧及时间戳后才原子发布视频与 `upload.json`。B 帧视频按解码后的呈现时间检查，不能把合法的包级重排误判为时间倒退。失败文件不进入模型，也不覆盖已有合格场景。

`video_input/recording.py` 统一协调采集、上传、准备、重建和展示。上传与录制/重建互斥；新任务绑定新视频与状态，旧 `ready` 或旧 viewer URL 不能使其提前完成。USB 缺失只影响摄像头预览/采集，不阻断电脑上传入口；预览恢复失败也不能把已经成功生成的场景改判为重建失败。

`initialize/camera_ui.py` 根据 `input_kind` 选择标定和预热环境。相同入口可复用预热进程，切换入口须关闭旧会话再准备新会话，避免沿用错误的相机参数。生成和渲染仍使用既有 NPU 与冻结 FPGA 路径；新增 UI 不是 CPU-only 替代链。

部署文件表 `initialize/board_sync.py` 已纳入上传模块和两个页面。`video_input/test_upload.py`、`test_recording_upload.py` 及 `initialize/test_camera_input_modes.py` 覆盖接收合同、入口隔离和预热切换。

## 状态与时间口径

保留 `READY → VIDEO_COMPLETE → SCENE_READY → FRAME_COMPLETE` 四事件。预热与视频输入只记录，不混入场景准备时间。

- USB 模式同时保存用户点击停止的时间和完整视频交付时间；页面到首帧计时不能在 `SCENE_READY` 或 `VIEWER_READY` 提前停止。
- 上传模式记录上传时长；板端收到最后一个字节即设置处理起点，后续探测、解码和准备必须计入。HTTP 返回或 ffprobe 完成不是新的、更晚的计时起点。
- 页面持续轮询；临时断网时计时继续，展示连接错误并阻止不确定状态下重复提交。只有当前视频对应的真实 `FRAME_COMPLETE` 才发布结果并冻结首帧计时。
- 结果页沿用左侧 Gaussian、参考方向与固定中心朝向选择，右侧确认后由 FPGA 返回画面的布局。支持 360° 控件不等于输入场景已覆盖 360°。

### 内存、守卫与尚未完成的对照

本次外层协调器进程树 PSS 采样峰值 **590.685 MiB**、最低 MemAvailable **221.895 MiB**；内层 pipeline 树 PSS 峰值 **503.211 MiB**、最低 MemAvailable **221.203 MiB**。两棵树嵌套，**不能相加**。测量覆盖预热、运行和 viewer 存续，结束状态为受控中断，不能把其 493/688 秒的总存续时间当成单视频处理时间，也不能把受控收尾误判为本次首帧失败。

FPGA 四路主线、BOOT 与资源配置未改。本轮未新测 FPGA 资源利用率、NPU 利用率、功耗或真实 DDR 流量。52.049747 秒尚未达到 20 秒目标；两次约 53 ms 的常驻换视角满足 1 秒方向，但仅是同场景两次请求，不能代表长期 P95/P99。

### 验收范围

这次已补齐普通两视图的 **电脑浏览器文件上传→板端 ARM 准备→十图 NPU 混合推理→FPGA 首帧→网页查看入口** 的实际执行与原始图像证据。它没有证明 USB 摄像头真实开始/停止录制、USB 到首帧链、固定中心 360°多帧对覆盖、任意尺寸/编码视频泛化或长时间稳定性；这些仍需各自实测。两个网页的合成状态截图和 40 模块软件回归也不能替代这些物理验收。实时连通性应由根任务当前连接核对，A 轮记录本身不保证服务此刻仍在线。
