# 2026-11-01 用户长录像选帧与空间保护修复

用户用按钮录制后重建失败，截图提示 No valid context pair。当前任务是检查这段真实素材、
恢复可用片段并修复界面/采集，不把所有失败归咎于用户录制时间。

## 实际原因与改动

原片：18.219 秒、1087 个 JPEG 包、59.6081 fps、130,245,020 字节，720p MJPEG。
镜头在拍摄中有较大倾斜、靠近和转向。旧程序全片均匀取 8 帧，间隔约 2.6 秒，
截图中的跨帧匹配只有 4～17 个，达不到既有 30 内点门槛；更长录像不会自动增加模型的两张上下文数量。

1. `video_input/decode.py` 增加有界候选 span，仍按实际 JPEG 包计数、保留原片索引。
   `scene_preparation.py` 保留原全片选帧；仅失败后依次尝试末尾/中部/开头约 4 秒窗口，
   最多 3 次局部回退，每轮 8 张默认候选、上限 12。通过即停止，不把整片解码帧常驻内存。
   input.json 记录失败全片尝试、选中 span、原片哈希和原索引。纯旋转、低视差、少内点、PnP 误差等门槛未放宽。
2. 旧 FFmpeg 4.2 Matroska `-fs` 不是硬文件大小限制：本片设定 96,493,568 字节，
   最终为 130,245,020 字节，超出约 32.19 MiB，导致根文件系统仅剩约 31 MiB。
   实机确认支持 cluster_size_limit / cluster_time_limit；按钮录制改用 1 MiB/250 ms 短 cluster，
   每 100 ms 主动检查文件与可用空间，提前约 8 MiB 请求 FFmpeg 正常收尾。
   同时对 FFmpeg 设置 Linux RLIMIT_FSIZE 硬上限，作为最后拒绝写入保护；触发硬保护而封装失败的文件不能交付重建。
   仍预留 64 MiB，单文件最多 256 MiB；这不是其他进程同时写盘时的系统全局配额。
   该补强适用于当前按钮双输出录制，不能把旧固定时长 capture_clip 的仅 -fs 行为表述为同等硬保护。
3. UI 新录像默认最长 10 秒，推荐 5～8 秒；错误正文改为拍摄建议，原始诊断放在折叠详情中。
   `--resume-clip` 校验完整标记、原片 SHA256、录制目录边界、模式和文件路径后，
   恢复这段原片，用户不必为服务更新重新录制。

仍使用用户授权的 FoV 95° 估算内参，focal-ratio=0.5256751337、零畸变。
这不是镜头实测标定，恢复链路不等于几何/画质验收。未改 Gaussian 模型或冻结 FPGA 算术。

核心复现仍为原 `pipeline.py initialize --video 原片 --auto-select --focal-ratio 0.5256751337 ...`，
不需要生成或重新编码裁剪短片；新局部回退自动生效。现有查看器通过页面按钮或
本机 18434 的带 token 链接访问，服务只监听板端 loopback，SSH 转发限制在电脑 loopback。

优势：保留用户原片，在不放宽几何门槛的情况下处理长片采样过稀；修复 `-fs` 软限制的真实超量，
页面给出可操作的拍摄建议并保留详细诊断。
代价：失败回退增加最多 3 次局部搜索/重解码，长片准备明显更慢；不能弥补原片快速转动、
遮挡、未标定和有限两视图覆盖。当前结果支持链路恢复和空间保护，不能支持画质、提速或节能结论。
下一次建议固定镜头朝向，静止有纹理场景、缓慢平移 5～10 cm，录 5～8 秒；
空间不足会提前停止，后续长期使用应安排专用存储或经用户决定归档原录像。
