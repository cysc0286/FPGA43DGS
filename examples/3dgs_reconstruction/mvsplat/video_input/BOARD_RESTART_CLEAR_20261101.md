# 再次启动与清空全部记录，2026-11-01

已修复“结束后再次点击开始连续重建没有反应”，新增“清空全部记录（含最新结果）”。
修改仅涉及输入页面、记录管理与 initialize 生命周期，不改变几何、模型、冻结 FPGA 程序或固件。

## 原因与修改

实际页面状态为 complete，最新连续会话已经发布两个有效版本。板端剩余空间约 122.8 MiB，
小于原有启动门槛 128 MiB。重放原开始请求确实得到 HTTP 409、空间不足；
页面的错误随后又被每 500 ms 状态刷新清空，所以用户看起来像没有点击成功。

现已将操作错误保留到下一次操作；保持原有空间保护门槛。
正常结束后回收非最新候选槽；再次开始前仅清理旧连续会话，保留当前会话和最新有效连续结果，
并校验完整帧哈希后回收备用槽。普通短片和普通场景不在自动清理范围。
由此避免连续多轮各积累两个场景槽，仍允许查看最后有效结果。

新增两种明确不同的操作：

- 清理历史记录（保留最新）：沿用原规则。
- 清空全部记录（含最新结果）：浏览器明确确认后，关闭已结束的查看器、等待工作线程退出，
  删除 sessions 内可识别的 clip_/scene_/stream_ 会话及配套日志，再清空短片、场景和计时状态。
  活跃录制/重建/连续采集或其他清理进行中会拒绝；token 与明确确认标志缺一不可。
  原来的边界及链接检查保持；未知目录、异常链接、权重和系统文件保留，并报告跳过项。

关闭查看器及等待线程时释放 camera.lock，避免工作线程 finally 恢复预览时互相等待。
新增保存连续结果恢复入口 `--resume-stream`；UI 重启可打开其最后已验证槽，不再次推理。
若用户已经清空记录，旧启动命令中的不存在恢复路径会被忽略，不阻止空页面启动。
已修正恢复过程中读取到旧 stopped 元数据就提前显示 ready 的状态判断。
