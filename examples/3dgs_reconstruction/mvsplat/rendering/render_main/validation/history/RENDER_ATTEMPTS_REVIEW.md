# 近几天换视角渲染尝试总复盘

审计日期：2026-10-06。主要范围：2026-10-01 至 2026-10-06；9 月 30 日作为当前主线的来源补充。依据现有源码、冻结记录、HLS/RTL 日志、物理报告和实板 JSON 整理。本次是历史证据审计，未新跑板测、综合或布局布线。

目标始终是：场景已加载，输入新相机，到完整 RGB 帧返回；完整场景为 32,768 Gaussian、128×128、Dense mode 2。不把视频初始化、训练、NPU、显示扫描或文件归档混入本次版本比较。16k 预览和 Sparse 单列为有损对照。

## 先看结论

1. **已证明并采用的改进**：9/30 四路 grouped-shared 硬件，以及 10/1 直接收集、存储复用、NEON 软件组合。主线仍为这组组合。
2. **有局部周期收益、没有足够整帧收益**：CTU II6 + 完整函数 ROM 上板后硬件周期只下降约 0.59%；没有证据支持显著端到端提速，已回退。
3. **有仿真潜力、但未成为可部署版本**：四路拆分流水在长列表 RTL 中减 46.33% 周期，但最终全板 WNS=-0.987 ns；三路拆分减 35.51%，多次物理实现仍未通过 setup。
4. **确实更快但画质明显损失**：16k 预览约 27.34 ms；Sparse mode3/5 约 32.9 ms。均不能作为“同等画质加速”的最佳版。
5. **更换了资源映射但无速度收益**：10/6 compact+SRL 三路候选已完整上板，FPGA 服务增加 10.91%，已回退。
6. **仍是正确性/协议问题**：DPC 交错与分块表存在较大数值差异；行表 FIFO 有真实 RTL 死锁。不能将它们归结为“器件性能已经到极限”。

主线历史正式软件验收 40.9671 ms；10/6 原版两组合计 43.9201 ms，回退后一组 42.9170 ms。它们是不同运行，不能拼接最小值宣布新收益。主线 FPGA 服务约 24.4 ms。历史同轮 CPU FP32 158.7076 ms、CPU+FPGA FP16 40.7409 ms，约 3.896 倍属于既有异构部署收益，不是本轮新机制收益。

## 如何读这些表

- 板端毫秒只表示完整帧；HLS II 和 RTL 周期单列，不换算成整帧加速。
- II 是流水发射间隔；内部 II=1 不证明跨高斯组无等待。
- HLS 资源只对应核估算；placed 为放置阶段；routed 才是最终路由网表资源。
- “停止”与“失败”分开：主动停止没有取得最终结论，不能冒称工具证明不可布线。
- 数值差异不自动等于肉眼明显退化；但没有全帧 PSNR/SSIM/图像，也不能认定满足允许小幅下降的要求。
- 本文保留每种独立机制和修复分支；同一源码的 synth/cosim 重跑不重复计算为新的算法版本。逐个构建、资源和完整统计见 [METRICS.md](attempts_audit/METRICS.md)；逐帧数据重算结果见 [board_runs.csv](attempts_audit/board_runs.csv)。
- 当前档案共提取57组配置/运行组合、37个HLS构建目录、29份物理时序报告；它们不是57个算法或37种架构。来源清单记录330个输入文件的SHA-256。

另外保留但不算算法版本的执行失败：CPU初次对照误带FPGA专用`neon_pack`参数被运行时拒绝，随后修正后完成；新harness配旧Python runtime被拒绝，随后同步runtime；Windows HLS过长IP路径导致生成失败，改短工程名后继续。它们属于测试入口/工具问题，不是CPU、FPGA或PipeGS机制失效。

## 八、归因复盘与后续优先级

### 已经有充分证据的结论

1. **做对热点的数据组织有收益。** B5的跨子块复用与S5的软件拷贝/初始化优化都完成实板验证。
2. **只加速前级不够。** H14短列表-14.8%，长列表仅-0.3%，实板约-0.59%硬件周期。短样本中过于突出的CTU开销不能代表真实场景。
3. **拆分流水在合适负载有潜力。** H13/H16长列表较快，但全板物理失败；P7三路又暴露真实场景比长列表压力用例慢。须针对真实帧的候选数量、掩码与早停分布验证。
4. **存储重映射不是必然节省资源。** B4/H15/P5都遇BRAM粒度开销；P7减少HLS BRAM后仍在全板几乎占满Slice。
5. **几类失败根本不是速度问题。** H8/H9/D6是握手死锁，P3是稀疏group属性来源错误，D2/D4是数值偏差；应先解正确性或活性。
6. **实验方法也造成过误判风险。** 外壳不一致、CPU后台抢核、把placed当routed、沿用过时摘要、挑最快运行，都已经在本表纠正。

### 下一轮优先处理什么

- 保留 B5+S5 作为部署主线，不把P7负结果替换进去。
- 先以真实帧重放统计有效/屏蔽请求及求值/合成/输入/输出阻塞，再单独减少空请求槽位或组间排空。数据宽度压缩已经证明不足。
- 对独立像素/Tile尝试有序上下文交错，但不要取消同像素的深度与透明度依赖。它需要新的调度和缓冲，不是再加一个pragma。
- DPC若继续，优先修D6请求/表的先后握手，并定位random36的大误差；不能仅把诊断阈值放宽。先全帧画质，再讨论精度/资源收益。
- 任何未来CTU或更多路数候选都固定精简外壳。只有带同源配置的实验才可用来判断资源上限。
