# Loaded-scene rendering: optimize the dominant stage

Scope: a new camera request to a complete 128x128 RGB frame, after the scene
has been loaded. Video input, MVSplat, NPU and scene preparation are excluded.

## Latest accepted board evidence

Source: `../results/20260930/view_switch_v4/parallel_results.json`, build
`parallel11`: 32,768 Gaussians, three views, ten repeats, two rounds, 60 frames.
The installed hardware is the four-lane exact-exp-ROM 200 MHz design.

| Non-overlapping wall-time stage | Mean ms | Share |
|---|---:|---:|
| FPGA service: packing, submit, execution, completion, readback/reassembly | 26.671604 | 58.99% |
| CPU projection | 7.607670 | 16.83% |
| CPU visible-point collection | 3.124217 | 6.91% |
| CPU radix sort itself | 2.419983 | 5.35% |
| CPU histogram/scatter into Tile lists | 3.125829 | 6.91% |
| RGB conversion | 1.231182 | 2.72% |
| Remaining camera/protocol/frame return | 1.031113 | 2.28% |
| **Complete frame** | **45.211598** | **100%** |

The collection/radix/scatter instrumentation has a small timing difference
from its outer `sort_ms` (8.670593 ms); do not sum nested timers twice. The
remainder above uses the separately measured substeps, and is arithmetic,
not a directly instrumented additional stage.

The hardware busy counter averages 5,215,434 cycles (26.077172 ms at 200 MHz).
It runs in `pipeline/rtl/flicker_dma.sv` while DMA `busy` is asserted, including
kernel execution, stalls and the final read-after-write fence. It is **not** a
pure arithmetic counter. CPU upload/wait/read timers overlap this interval;
they must not be added to it to manufacture a larger frame time.

For comparison, the earlier **16,384-point preview** was 31.931891 ms, with
17.875974 ms in FPGA service (55.98%). This is a different lossy profile and
an older software/hardware version, not a regression from 32 ms to 45 ms.
It has not yet been remeasured with the latest software.

## Priority and attainable savings

1. **Kernel state transfer and short-batch bubbles.** The baseline evaluator
   launches 16 pixel iterations at II=1, but has a 117-cycle pipeline depth
   and a 133-cycle call latency. Each Gaussian/mini-tile also loads and stores
   pixel state in two 17-cycle loops; the lane waits for that ordered work to
   finish before accepting the next contribution. Test faster state transfer
   first, then consider interleaving independent mini-tile contexts so useful
   work fills the pipeline. Same-pixel contributions must retain their depth
   order; suppressing true dependencies is not a valid acceleration.
2. **CPU projection and Tile-list production.** Together these are about
   16.28 ms. Exploit view coherence, compact native loops and work reduction
   after the FPGA comparison. Pure sorting is only 2.42 ms: even eliminating
   it entirely saves at most 5.35% on this measured path, before replacement
   overhead or extra rendering work.
3. **Physical timing after the architecture change.** Investigate placement,
   fanout and local register/memory connections on the actual critical path.
   Raising clock frequency alone does not remove pipeline bubbles. The shared
   200 MHz domain and vendor paths prevent assuming a renderer-only clock
   increase is safe. Accept a hardware candidate only after routed timing and
   matched board data, preserving the previous BOOT for rollback.

Illustrative Amdahl calculation only: halving the entire 26.671604 ms FPGA
service stage would change 45.211598 ms to 31.875796 ms if other stages stay
unchanged. This is not a prediction or a measured result.

## This increment

Opt-in state-transfer and grouped-subtile candidates, including rejected attempts,
are documented in [lane_workset](../../../3dgs_flicker_hw/pipeline/lane_workset/README.md).
The grouped-register candidate merges up to four subtiles of one Gaussian into
one ordered 64-pixel traversal, eliminating repeated scratch load/store and
pipeline drains. Current production is mode 2; its same-input three-Tile DMA/CDC
RTL test falls from 4861 to 3442 cycles (29.19%). Six modes match the frozen
pixel reference, plus 36 varied Tiles pass C-model comparison in all six modes.

This is **not a new board result or full-scene benchmark**. HLS BRAM_18K falls
219 to 203, FF rises 64227 to 92935, LUT rises 34927 to 38011, DSP stays 244.
These are renderer HLS estimates, not whole-board physical utilization. Sparse
single-subtile groups can lose efficiency; matched scene testing is required.
No placement/routing, installation or new board timing was performed: SSH timed
out and the host Ethernet adapter reported disconnected on September 30, 2026.
The installed renderer and default source configuration remain unchanged.
