16k 有损预览 **27.337 ms**。详细同输入对照、资源和图像见

下面保留此前的软件优化记录，其“硬件未改变”只指当时那轮实验。

本轮只测：场景及硬件环境已经常驻后，提交新相机位姿，到完整 RGB 帧返回。
不包括视频输入、位姿重建、MVSplat、模型生成、图像归档或显示器扫描输出。
128×128、32,768 个高斯、同一组 3 个留出视角，未减少高斯数量或渲染精度。

作为同轮基准重新执行；不能将前后不同轮次的小波动解释为新的优化。

## 改了什么，以及为什么有效

1. 将计时中的“排序”拆成收集记录、深度排序、Tile 列表生成，避免把整个
   12 ms 都误认为排序算法的开销。
2. `depth_sort.hpp` 使用 11 位一趟的稳定基数排序：32 位正 FP32 深度仍
   全部参与排序，只将四趟扫描改为三趟，深度精度和相同深度的 ID 顺序不变。
3. `tile_lists.hpp` 让四核各处理连续的一段深度有序高斯。先分别统计每个
   Tile 的数量，再按工作块顺序做前缀和，最后并行写各自独占的区间。
   因此同一 Tile 内仍保持原来的前后顺序，没有并发追加或合成次序竞争。
4. 复用计数、列表和排序缓冲；相机请求、常驻 C++ 进程、FPGA 提交协议保持原接口。

这次收益来自 C++ 内的数据处理和四核分工，而不是把已经是 C++ 的热路径
换一种语言。CPU 投影此前就已使用四核；这次补上后面的分组并行。

| 同轮阶段平均 | 旧程序 ms | 新默认 ms |
|---|---:|---:|
| 投影 | 7.637 | 7.608 |
| 收集＋排序＋Tile 列表 | 12.088 | **8.671** |
| FPGA 提交、执行、回读与结果整理 | 26.672 | 26.672 |
| RGB 转换 | 1.230 | 1.231 |

新分组内部为收集 3.124、排序 2.420、并行计数与分发 3.126 ms。
阶段和不包含全部协议、相机解析和帧返回开销，最终以 `wall_ms` 为准。
上传约 2.494、等待 15.186、回读 0.677 ms 属于 FPGA 阶段内部统计；存在
重叠，不能再与该阶段相加。首视角逻辑输入 3,441,984 字节、输出
262,144 字节，不是 DDR 总线流量实测。

单独的基数宽度对照也保存了负结果：同一轮基准 48.589 ms，8/11/16 位
版本分别 48.742/48.227/49.779 ms。16 位虽然只扫描两趟，但更大的计数
数组并未带来板端收益，没有选择它作为默认。

## FPGA 布线判断与下一步

本轮读取既有最终布线报告，没有重新生成位流。渲染/DMA 的 setup/hold
余量是 +0.316/+0.050 ns；共享 200 MHz 域最差 setup 只有 +0.034 ns，
落在原厂视频缓存使能路径，4.520 ns 延迟中 4.175 ns 是布线延迟。
因此不能仅根据渲染模块的余量直接提高全板共享时钟。

单纯减少布线延迟、仍按相同 200 MHz 与相同周期执行，不会自动减少帧时间。
布线改善可以为更高频率或更紧凑的流水创造条件，但必须重新实现并上板测量。
此前的 ROM 改造已真实减少硬件周期 6.37%；这是上一轮的硬件收益，不能
再次计作本轮的软件收益。

当前 FPGA 帧计数约 5.215 百万周期，200 MHz 下对应约 26.08 ms，解释了
26.67 ms 硬件阶段为什么几乎没被这次 C++ 优化改变。进一步的主要机会是
`pipeline/pipeline.cpp` 中 `render_lane` 的串行工作集装入、
`evaluate_mini`、写回，以及每个短像素批次的流水填充和排空。
下一次硬件候选应评估多个独立 Mini-Tile 上下文交错执行，保持同一像素
的合成顺序，以减少这些等待；这是待实现验证的设计，不是已得到的加速。
不能用删除真实依赖声明、盲目升频或跳过正确性来代替这项结构修改。

全板资源仍是上一轮布线报告：LUT 76.84%、FF 62.04%、BRAM 85.47%、
DSP 63.0%、Slice 99.16%。继承的两处 AI 脉宽违例仍在，不宣称全板时序签核。
原生并行化不改变这些 FPGA 资源数字。
