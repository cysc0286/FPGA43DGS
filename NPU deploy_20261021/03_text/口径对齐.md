# 口径对齐：我们的数字 vs 仓库的 27.88 s（2026-10-21）

## 一、仓库口径到底是什么

仓库对外报的主指标是**"视频结束到首帧"**，默认入口 `warm_cpu_default_v6`（4 线程串行）实测 **28.066 s**，
三次平均 **27.876 s**。分解如下（引自 `BOARD_WARM_NPU_VALIDATION.md`）：

| 阶段 | 秒 | 边界 |
|---|---:|---|
| 解码、两视图几何与目标 PnP | 8.849 | prepare 内部 |
| **网络前向** | **13.331** | 不含权重加载 |
| 前向、输入检查、Gaussian 保存等 | 14.327 | 包含上述前向 |
| 高斯导出 | 2.789 | 导出内部 |
| VIDEO_COMPLETE→SCENE_READY | 27.178 | 含哈希、接口与装入开销 |
| SCENE_READY→首帧完成 | 0.888 | 含完整帧和哈希检查 |
| **主计时（首帧）** | **28.066** | 后两项之和 |

## 二、我们测的数字对应哪一项

我们跑的是 `verify_diagnostic`，读的是 `inference.json` 的 `inference_seconds`。

板上同目录的 `warm_cpu_default_v6/inference/inference.json` 给出：

```json
"threads": 4,
"inference_seconds": 13.3306,      ← 与文档"网络前向 13.331"逐位一致
"process_seconds": 14.3269         ← 与文档"前向+检查+保存 14.327"一致
```

**结论：`inference_seconds` 就是仓库那张表里的"网络前向"。**
所以 `to_gaussians` 省下的时间**正好落在 13.331 s 这一项里**，可以直接从 28.066 s 里扣。

## 三、但有一个必须先纠正的差异：线程数

| | 仓库默认入口 | 我们的诊断跑 |
|---|---:|---:|
| 线程数 | **4** | **2** |
| `inference_seconds` | 13.331 s | 20.471 s |
| backbone 段耗时 | 4.113 s | 5.979 s |

`verify.py` 里把线程数写死成 2：`ModelRuntime(a.weights, a.vendor, 2, 16, ...)`。
**所以我们的基线比仓库慢了 1.54 倍**，那个 −26.3% 是**在更慢的基线上算出来的**。

这一点很关键：**NPU 的时间是固定的（0.675 s），CPU 的时间随线程数变**。
线程越多，CPU 越快，NPU 的相对优势就越小。

## 四、换算到仓库口径

`to_gaussians` 在 NPU 上耗时 **0.675 s**；在 2 线程 CPU 上约 **6.06 s**（= 5.38 省下的 + 0.675 NPU）。

线程加速比用两个已有数据夹住：

| 参考 | 2 线程 | 4 线程 | 加速比 |
|---|---:|---:|---:|
| backbone 段 | 5.979 | 4.113 | 1.454× |
| 整体 inference | 20.471 | 13.331 | 1.536× |

估算 4 线程下 `to_gaussians` 的 CPU 耗时：

```
6.06 / 1.454 ≈ 4.17 s   （上界）
6.06 / 1.536 ≈ 3.94 s   （下界）
```

对应节省：**4.17−0.675 ≈ 3.49 s** 到 **3.94−0.675 ≈ 3.27 s**

换算成仓库的主指标：

| 项 | 数值 |
|---|---:|
| 仓库基线（首帧，4 线程） | 28.066 s |
| 网络前向（4 线程） | 13.331 s |
| 扣掉 `to_gaussians` 的节省 | −3.27 ~ −3.49 s |
| **预期首帧** | **24.58 ~ 24.80 s** |
| **相对加速** | **约 −12%** |

## 五、所以对外该怎么说

**不能说**："端到端快 26.3%"。

**应该说**：

> 在 2 线程配置下，`to_gaussians` 子图迁移到 NPU 使网络前向从 20.47 s 降到 15.09 s（−26.3%）。
> 换算至仓库默认的 4 线程入口，预计首帧从 28.07 s 降到约 24.6–24.8 s（约 −12%），
> 因为 NPU 耗时固定、CPU 侧随线程数变化，线程越多 NPU 的相对优势越小。

**6 线程或更高**的话，这个比例还会继续下降——`to_gaussians` 的 CPU 时间会被进一步压缩，
而 NPU 的 0.675 s 降不下去。

## 六、还有一个没测的数

上面 3.27~3.49 s 是**估算**，用了两个不同分区的线程加速比夹出来的区间。

要把它变成实测值，只需用 4 线程跑一次 `to_gaussians`（我们的诊断脚本加一个 `--threads` 参数即可，
`verify.py` 本身仍保持 2 线程不动）。跑完就能得到：

- 4 线程 CPU 基线（用于和 13.331 对齐验证）
- 4 线程 + NPU 的 `inference_seconds`
- 两者之差 = 真实节省，直接扣到 28.066 s 上

**这一步大约 2 分钟一次，是让这个数字能站住的最后一步。**
