# 图像级验证结果：NPU 高斯的画质影响（2026-10-20）

## 一句话结论

**`depth_head` 走 NPU 后，数值门禁判"失败"（max_abs 0.2298），但画面差异只有 67 dB 的等价性、
对真值的 PSNR 变化在 ±0.005 dB 以内——肉眼完全不可分辨。**

这是第一次把"数值误差"和"观感"放在同一张尺子上比较。

---

## 方法（保证控制变量）

| 环节 | 做法 |
|---|---|
| 输入 | **同一份** `candidate/input`（同一 `context.npz`，SHA 绑定校验） |
| 位姿/内参 | 两套完全相同，因为都来自同一次 `runtime.infer` |
| 高斯来源 | `cpu/gaussians.npz` vs `hybrid/gaussians.npz`（唯一变量） |
| 渲染器 | **同一个** NumPy SH3 泼溅器，同一份代码、同一相机、同一顺序 |
| 真值 | `input/images/<target>.png`（留出帧，未参与重建） |
| 指标 | PSNR（RGB，[0,1]）+ SSIM（11×11 高斯窗 σ=1.5，逐通道平均） |

因为两套高斯走的是同一条渲染代码，**任何分数差异只能来自高斯本身**，不是渲染器差异。

## 结果

| 视角 | CPU vs 真值 | NPU vs 真值 | ΔPSNR | NPU vs CPU |
|---|---|---|---|---|
| `frame_000007` | 20.1964 dB / 0.77133 | 20.1955 dB / 0.77129 | **−0.0010 dB** | **67.18 dB / 0.999977** |
| `frame_000015` | 20.2329 dB / 0.80727 | 20.2281 dB / 0.80728 | **−0.0048 dB** | **67.17 dB / 0.999971** |
| `frame_000022` | 24.1842 dB / 0.82982 | 24.1844 dB / 0.82979 | **+0.0002 dB** | **67.01 dB / 0.999975** |

三点观察：

1. **NPU vs CPU = 67 dB。** 一般认为 40 dB 以上就"肉眼不可分辨"，67 dB 属于数值噪声级别。
2. **对真值的 PSNR 变化在 ±0.005 dB 内**，而且第 3 个视角甚至略高（+0.0002）——
   说明这点误差连"方向"都不稳定，完全是噪声，不是系统性劣化。
3. **CPU 基线 20.20 / 20.23 / 24.18 dB**，与仓库公开的 19.45–21.35 dB 同一水平，
   说明这套准备流程 + 渲染器没有系统性偏差，数字可信。

## 这次对比的"难度"其实是最高的

`depth_head` 是历史上**单分区误差最大**的一个（max_abs 0.2298，是 backbone 的 5.8 倍）。
用它做第一个试验，等于挑了最坏的那个分区来看画质影响——**它都没问题，其他更小的分区更不会有问题。**

## 局限（必须一起说）

| 局限 | 说明 |
|---|---|
| 只有 1 / 7 个分区走 NPU | 其余 6 个仍在 CPU（因为七会话会互相污染，见下） |
| 渲染器是自研 NumPy 泼溅 | 不是 FPGA 渲染器，也不是官方 CUDA；只能做**相对**比较，不能当绝对画质指标 |
| 只用 SH3（前 16 系数） | 与渲染 ABI 的截断一致；SH4 的贡献未计入 |
| 单场景、3 个视角 | 样本小，但三个视角高度一致 |
| 未测 LPIPS / 闪烁 | 与仓库现状一致（他们也没测） |

## 与数值门禁的关系

| | 数值门禁 | 画质 |
|---|---|---|
| 判据 | 逐元素 `rtol=2e-3, atol=2e-4` | PSNR / SSIM |
| `depth_head` | **失败**（max_abs 0.2298） | **通过**（差异 67 dB） |

**同一份高斯，一条判据判死，另一条判活。** 这说明 `2e-4` 这道门禁与"画面能不能看"之间没有对应关系：
它是一个用 FP32 参考实现的容差，套在了 10 位精度的硬件上。

## 附带发现：七会话互相污染（实测证实）

七个分区同时挂在一个 worker 上时：

```
backbone_cnn       max_abs 0.0400121808052063   ← 与 9/29 历史记录逐位一致
regressor_residual max_abs 0.011614799499511719
depth_head         报 Nonfinite output，worker 崩溃
其余 4 个          "Partition worker is closed or failed"
```

而 **`depth_head` 单独跑完全正常**，并成功产出高斯。

同一个分区、同一份输入、同一块板，**只改"同时开几个会话"，结果从正常变成 NaN**。
这证实了代码审计阶段提出的假设：七个会话共享同一设备基址、各自 `apply()`，会互相覆盖权重。

## 全分区扫描（7 个分区各自单独走 NPU）

每个分区单独跑一次：只有它在 NPU，其余 6 个留 CPU。取三个留出视角的均值看不出来，
所以列出三个视角的 NPU-vs-CPU PSNR，以及最差的那个。

| 分区 | oracle max_abs | 视角 7 | 视角 15 | 视角 22 | 最差 NPU-vs-CPU |
|---|---:|---:|---:|---:|---:|
| `depth_head` | 0.22975 | 67.18 | 67.17 | 67.01 | 67.01 dB |
| `to_gaussians` | 0.20767 | 64.02 | 63.74 | 63.87 | 63.74 dB |
| `backbone_cnn` | 0.04001 | 63.60 | 66.00 | 66.17 | 63.60 dB |
| `regressor_residual` | 0.01161 | 81.31 | 81.91 | 77.06 | 77.06 dB |
| `proj_feature` | 0.00236 | 78.49 | 76.35 | 78.68 | 76.35 dB |
| `upsampler` | 0.01536 | 51.40 | 50.00 | 50.24 | **50.00 dB** |
| `to_disparity` | 0.02727 | 45.87 | 45.04 | 44.01 | **44.01 dB** |

**七个分区全部在 44 dB 以上**，按通行口径（40 dB 以上肉眼不可分辨）全部属于"看不出差别"。

对真值的 PSNR 变化（NPU 减 CPU）最大也只有 **0.05 dB**，而且有正有负：
`upsampler` 在视角 22 上反而比 CPU 高 0.038 dB，`to_disparity` 在视角 15 上高 0.023 dB。
**误差连方向都不稳定，是噪声不是劣化。**

### 最重要的一条：数值门禁的排序和画质影响的排序，是反的

| 分区 | max_abs 排名 | 画质影响排名 |
|---|---|---|
| `depth_head` | 最大（0.2298） | **最好**（67 dB） |
| `to_disparity` | 第 5（0.0273） | **最差**（44 dB） |

`to_disparity` 的逐元素误差只有 `depth_head` 的 **1/8.4**，但它的画面影响差了 **23 dB**。

原因不难理解：`max_abs` 是分区出口的逐元素绝对差，而画质取决于这个误差在网络里
**往哪儿流、被谁放大**。`to_disparity` 输出的是视差，直接决定高斯的深度排序和位置，
一个 0.027 的视差误差落到图像上就是像素级错位；`depth_head` 的特征还要经过多层抽象才到高斯。

**结论：拿 `2e-4` 这种逐元素阈值当验收门禁，测的东西和想保证的东西不是一回事。**
