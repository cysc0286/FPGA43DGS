## 0. 先说结论

**"能不能把推理部署到 NPU" 这个问题，仓库已经回答过了：能，且已经跑在真实板子上。**
七个 MVSplat 子图（25 个卷积、127 个 HardOp）用 ICraft 3.36.1 编译后，已在真实 ZG330 设备上执行，
每个分区单独进程、同输入两次输出可重复。

真正卡住的是两件事：

| 卡点 | 现状 | 性质 |
|---|---|---|
| **① 数值门槛不通过** | 7 个分区全部失败（逐元素 `rtol=2e-3, atol=2e-4`） | 技术问题，可攻 |
| **② 数值失败的原因未定性** | 首层真实权重 38.10% 元素越界，FP16/TF32 舍入都解释不了；SDK `precheck()` 报 `opid:241` 权重错 | 根因未知 |

所以我的工作不是"再做一遍部署"，而是**把这两个卡点推到底，并给出真实收益数字**。

还有一个更根本的风险，仓库尚未验证，必须提前说（见 §5 R4）：
**冻结渲染器的位流 Slice 已占用 99.84%，NPU 与渲染能否共存于同一个位流里，没有任何证据。**

### 0.1 什么才算成功（目标阶梯）——"7 个分区全过"不是终点

用户方确认：**ZG330 就是板上的 NPU**（AI_Mate 是把它集成进 PL 的 EDIF 网表，ICraft 是编译它的工具链）。

但验收目标必须分层，否则容易把手段当目的：

| 层级 | 判据 | 当前状态 |
|---|---|---|
| **G0** | 单分区在板上输出与 oracle 数值一致（最小可复现单元） | 最小"已知权重"单卷积通过；真实网络首层失败 |
| **G1** | 7 个分区分别通过 L1 逐元素门槛 | **0 / 7** |
| **G2** | 单分区 NPU 整段耗时 < CPU 整段（含布局打包、IPC、SDK 写入/等待、SFB 转换、解包） | 未测 |
| **G3** | 选定分区组合后，高斯级误差在精度预算内 | 未测 |
| **G4** | **整链 VIDEO_COMPLETE → FRAME_COMPLETE 显著低于 27.88 s，且画质守住 PSNR≥20 dB / SSIM≥0.7** | 未测 |
| **G5** | NPU 与冻结渲染器共存于同一个可启动系统（同一位流或可靠分时） | 未验证 |

三点必须说清楚：

1. **G1 是必要不充分。** 七个分区全过，也可能整链一点不快——因为全分区逻辑 I/O 是 79.5 MiB/次，
   而 `upsampler` 18 MiB、`proj_feature` 20 MiB、`to_gaussians` 30.875 MiB 这几个大头，
   搬运成本可能直接吃掉核内收益。仓库此前的 NPU 匹配实验就是活例子：
   核内 forward 20.9 ms，整段却比 CPU 慢 3 倍。
2. **G1 甚至可能不必要。** 目标是 G4，不是"七个都上"。一个分区如果过了门槛但更慢，
   正确做法是**留在 CPU**，而不是为了"全绿"硬上。反之，只要有一两个净收益分区把整链打下来，
   哪怕另外几个永远留在 CPU，这件事就算成了。
3. **G5 是一票否决。** 如果 NPU 位流和渲染位流挤不到一起，前面全部白做。这条要最早问。

因此本文后续围绕 **G0→G2→G3→G4** 推进，G1 只作为定位 bug 的中间检查点；
是否"七个全过"不作为交付标准。

### 1.2 FPAI DEMO 说明（PDF，8 页）

这是唯一描述 NPU 使用方式的材料，信息量很大：

- **工具链锁死 Vivado 2018.03**（不是新版，版本对不上会直接失败）。
- FPGA 工程结构：`constrs_1/`（`ai7030.xdc`、`impl_constraints.xdc`）、`PS_AI IP`、`rtl/`（含 `edif/`、`ai7030_edif_top.v`、`AI_Mate_stub.v`、`sdi/`）。
- **NPU 以 EDIF 网表形式交付**：`AI_Mate.edif`（带 DetPost 硬算子）或 `AI_Mate_no_detpost.edif`（省 PL 资源）。
- 板型管脚差异：悟净 Lite 用 `PACKAGE_PIN R6/R5`（`FMC_HPC_GBTCLK0_M2C_C_P/N`）。
- 参考数据流：SDI → PL `rx_sdi` → 分两路 → PL DDR（喂 AI）＋ PS DDR（喂 HDMI）→ PS 启动 AI → AI 写回 PL DDR → PS 后处理 → HDMI。
- **PS 侧 API**（裸跑 C++）：
  - 寄存器：`device.defaultRegRegion().read/write(addr, ...)`，地址空间 `0x400C0000~0x400FFFFF`
  - PL DDR：`device.defaultMemRegion().malloc(size, auto_free, alignment)`，`mem_chunk.read/write(offset, ...)`
  - custom op 用寄存器轮询完成标志。
- PS 工程样例：`examples/1_single_input+ai/`，含 `imodel/`（网络模型）、`configs/`、`sdicamera+yolov5+hdmi.cpp`。

**关键推断**：这块板的 NPU 不是"像 RKNN/Vitis AI 那样有标准量化工具链的加速器"，
而是**以网表形式集成进 PL 的 AI IP，靠寄存器 + PL DDR 显式搬运数据**。
DEMO 给到"怎么跑一个已编译好的 yolov5"，**没有给"怎么把新模型编译成 imodel"的完整说明**——
这正是仓库用 ICraft 3.36.1 在补的那一环。

1. **首层真实权重失败**：`prefix_00` 最大误差 0.0924683，**38.10% 元素越界**，两次结果一致；

## 2. 我的判断：根因在哪

按可能性排序，这三条要逐个排除，不能跳：

**R1｜权重上传/读回与布局（最可能）**
证据链最硬：最小"已知权重"单卷积**通过**了；换成真实网络第一层就 38% 越界；
`precheck()` 直接报 PLDDR 里的权重不对；且 FP16/TF32 舍入**算不出** 0.09 这个量级的误差。
如果只是精度不够，误差应随数值量级线性增长、越界比例不该这么高。

**R2｜精度模式实际不是 TF32**
"输出 100% 落在 FP16 格点"意味着下游拿到的是 FP16 量化结果。
若属实，则 `depth_head`（0.23）和 `to_gaussians`（0.21）的误差量级就说得通了——
FP16 的 10 bit 尾数对深层特征确实不够。

**R3｜多会话/设备状态交互**
七会话并行时突发非有限值、单会话正常。可能是共享缓冲/映射或设备上下文覆盖。

**R4｜（工程级，尚未被提及）位流共存**
冻结渲染器 Slice 99.84%、LUT 77.94%、BRAM 82.45%、DSP 63.00%（仓库实测）。
AI_Mate 是集成进 PL 的网表，要占 PL 资源。**"NPU 加速"与"FPGA 渲染"目前是两个位流**，
仓库自己也把"NPU 与既有 FPGA 渲染共存"列为待验收项。
即便数值全过，如果两者挤不进同一个位流，这条路整体不成立。
**这一条必须最早问清楚，否则可能做完数值发现白做。**

## 4. 预期与风险（先说清楚可能白忙）

| 情形 | 概率判断 | 结果 |
|---|---|---|
| R1 是布局/上传 bug，修好后误差回到 1e-3 量级 | 中等 | backbone 等卷积密集分区可上 NPU，场景准备时间有实质下降 |
| 只有部分分区可用 | 较高 | 收益有限。注意 I/O：`upsampler` 18 MiB、`proj_feature` 20 MiB、`to_gaussians` 30.875 MiB，全分区逻辑 I/O 79.5 MiB/次——搬运成本可能吃掉核内收益 |
| SDK 精度路径不可控 | 中等 | 只能写负结果报告，转向其它 NPU 工作量（如 XFeat 特征前端） |
| R4 位流挤不下 | 未知但致命 | 整条路线需要重新设计（例如分时复用位流、或放弃共存） |

一个必须先记住的历史教训：仓库此前的 **NPU 描述子匹配是负结果**——
CPU 225.5 ms，NPU 常驻 + CPU 精确重算 668.2 ms，三对比值 2.96/2.91/3.00。
核内 forward 只有 20.9 ms，但 SFB 回读转换 44.3 ms、精确重算 126 ms。
**"核内更快"从来不等于"整段更快"。** D1 必须按整段计时，不接受只报 forward。

## 9. 从当前状态到"NPU 部署成功"的完整路径

§3 的 A–D 是"我怎么做"，这一节是"项目要走完哪些步"，视角不同，两者互补。

现状：7 个子图已编译、已在板端执行、0/7 通过逐元素门槛；高斯级与图像级从未测量；
无任何可信加速比；位流共存未验证。基线：首帧 27.88 s，画质 19.45/20.22/21.35 dB。

| # | 阶段 | 要做什么 | 出口判据（不满足就停） | 需要板子 |
|---|---|---|---|---|
| 0 | 取证 | 拿到板子/SDK/权重；确认板子当前状态；**先问位流共存** | 能复现仓库的失败（38.10% 越界） | 部分 |
| 1 | 根因定性 | 跑会话隔离实验；按通道统计越界比例；区分"H1 会话污染 / H2 分区自身 / H3 权重布局" | 能用一句话说清 38% 越界的机制 | 是 |
| 2 | 修复 | 按结论改：单会话串行 / 修布局 / 修权重上传 | **至少 `backbone_cnn` 单分区过 L1** | 是 |
| 3 | 性能判定 | `backbone_cnn` 的 NPU 整段 vs CPU 整段（含搬运） | 明显更快才继续；不快就换分区，全都不快 → 写负结果 | 是 |
| 4 | 精度预算 | 逐分区注入误差，算高斯级与图像级影响；定组合 | 高斯级误差在预算内，图像 PSNR/SSIM 不破门槛 | 否（有权重即可） |
| 5 | 整链接入 | `--backend npu` 接 `initialize`，跑完整视频 | 首帧时间 < 27.88 s 且画质守住 | 是 |
| 6 | 工程化 | 内存余量、重复运行一致性、失败回退、文档 | 连续多轮稳定；换输入不崩 | 是 |

### 三个决策点（每个都可能让项目终止）

1. **G5 位流共存**——必须在阶段 2 之前有答案。渲染器 Slice 99.84%，AI_Mate 要占 PL。
   挤不进去 ⇒ 后面全白做。
2. **阶段 3 的"真的更快"**——仓库已经有过一次 NPU 匹配的负结果（核内 20.9 ms、整段慢 3 倍）。
   如果卷积也是这个结局，说明这板的 NPU 对当前数据搬运方式不划算，应当尽早止损。
3. **阶段 4 的精度门**——如果 TF32/FP16 确实撑不住高斯参数，只能接受"部分分区上 NPU、
   其余留 CPU"，收益上限要重算。

### 最坏情况也是可交付的

即使阶段 3 判定"没有净收益"，产出仍然是一份完整的负结果报告：
根因机制、分区级误差与耗时数据、以及"为什么这块板的 NPU 不适合这条链"的量化论证。
仓库自己的历史文档就是这么处理 NPU 匹配失败的——这在他们那儿是**可接受的交付形态**。
