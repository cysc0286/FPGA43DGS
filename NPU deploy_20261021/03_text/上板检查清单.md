# 上板检查清单（拿到板子后的第一小时）

目的：在写任何代码之前，先确认"板子本身能不能跑 NPU"。
顺序不能跳——如果第 5 步（官方 demo）不通，后面的分区验证全是白费。

## 0.0 上电与串口（2026-10-20 实测补充）

板子型号 `FPAI_30TAI-LITE`（复旦微悟净 Lite），随箱配件：12V 电源、MINI USB 串口线、JTAG 转接头。

| 步骤 | 动作 | 依据 |
|---|---|---|
| 1 | 启动跳线帽保持出厂设置（QSPI Flash），不要乱动 | 硬件手册 §4.4 |
| 2 | **MINI USB** 线插板上丝印 `USB UART` 的口（不是 HOST 口） | 手册 §4.10，CP2103GM |
| 3 | 12V 适配器插 `DC` 座（J37） | 手册 §4.21 |
| 4 | **拨码开关 SW8 拨到 ON**（这是电源开关，插上不会自动通电） | 手册 §4.21 |
| 5 | 串口 **115200 8N1**，读启动日志 | 见下 |

**驱动问题（本机实测）**：Windows 默认不带 CP210x 驱动，设备管理器会显示
`CP2103 USB to UART Bridge Controller` 带黄色感叹号，错误码 **28**（驱动未安装），
且**不会分配 COM 口**。

- 驱动已下载并校验签名（`.cat` 由 Microsoft WHQL 签，`.sys` 由 Silicon Labs 签）：
  `D:\WorkBuddy\2026-10-18-20-37-46\drivers\cp210x\silabser.inf`
- 安装需要管理员权限：右键 `silabser.inf` → **安装**；或在管理员 PowerShell 里
  `pnputil /add-driver "...\silabser.inf" /install`
- 装完若仍无 COM 口，**拔插一次 USB** 触发重新枚举。

**串口工具**：`npu_deploy/tools/serial_console.py`

```bash

python tools/serial_console.py --send "uname -a" --wait 3      # 发命令收输出
```

## 0. 先分清三样东西

| 名字 | 是什么 | 跑在哪 | 和 Vivado 的关系 |
|---|---|---|---|
| **`.bit` 位流** | PL 里固化好的电路，含 AI_Mate 网表（NPU） | 板子 PL | **Vivado 的产物**。已有 `.bit` 就不用开 Vivado |
| **ICraft SDK · 编译器** | `icraft-parse/optimize/quantize/adapt/generate` | **PC**（仓库看到的是 `.exe`，即 Windows） | 无关 |
| **ICraft SDK · 运行时** | `libicraft*.so`、`icraft-xrt` 头文件 | **板子**（aarch64 Linux） | 无关 |

**结论：部署推理不需要 Vivado。** 只有要改 AI_Mate 的配置（例如换 `no_detpost` 版省 PL 资源）
或重新综合位流时才需要 Vivado 2018.03。

## 1. 连上板子

```bash
ssh <user>@<board-ip>        # 或串口 115200
uname -a                     # 期望 aarch64 / arm64
cat /etc/os-release          # 记下发行版版本
free -m                      # 记下可用内存（仓库记录过余量 266 MiB 很紧）
df -h /                      # 仓库提到过 SD 空间不足，要留余量
```

**记录**：CPU 核数、内存、可用磁盘。后面跑分区时要靠这些判断会不会 OOM。

## 2. 找 SDK 运行时（板子上）

不要假设路径，直接搜：

```bash
find / -name "libicraft*" 2>/dev/null | head
find / -name "session.h" -path "*icraft*" 2>/dev/null | head
ls -d /root/heterogs_npu/sdk_3.36.1/usr 2>/dev/null   # 仓库用过的路径
```

**期望**：能找到 `libicraft*.so` 与 `icraft-xrt/core/session.h`。

- 找到 → 记下 `<SDK>/usr/lib/aarch64-linux-gnu` 和 `<SDK>/usr/include`，后面要设 `LD_LIBRARY_PATH`
- 找不到 → **卡在这里**，需要向厂商/负责人要 SDK（这是硬阻塞）

## 3. 找 NPU 设备与驱动（板子上）

```bash
ls /dev | grep -i -E "npu|zg|ai" 
dmesg | grep -i -E "zg330|npu|icraft" | tail -20
lsmod | head -20
```

**期望**：能看到对应设备节点或驱动加载记录。
**如果什么都没有** → 板子上的位流可能不是带 AI_Mate 的那个（见第 6 步）。

## 4. 找仓库与既有产物（板子上）

```bash
ls -d /root/heterogs_npu 2>/dev/null
find / -maxdepth 4 -name "re10k.ckpt" 2>/dev/null
find / -maxdepth 5 -name "libmgs_npu.so" 2>/dev/null
find / -maxdepth 5 -name "manifest.json" -path "*compiled*" 2>/dev/null
```

**期望**：能找到仓库、权重、已编译包。
**找到已编译包就是好消息**——可以跳过重新编译，直接进第 7 步验证。

## 5. 最关键的验证：官方 demo 能不能跑

这一步不验证我们的网络，只验证**"这块板的 NPU 是活的"**。

FPAI DEMO 里的参考设计是 `sdicamera+yolov5+hdmi`，配套可执行在：
`examples/1_single_input+ai/PLin+SingleNet+HDMI/`（见 DEMO 说明第 5 页）。

```bash
# 在板子上找到 demo 目录后
ls examples/1_single_input+ai/*/
./adder_demo          # 先跑加法器 demo（最简单，只验证寄存器 + PL DDR 通路）
```

**判据**：

| 现象 | 说明 | 下一步 |
|---|---|---|
| 加法器 demo 通过 | 寄存器读写 + PL DDR 通路正常 | 继续第 6 步 |
| 加法器通过、yolov5 通过 | **NPU 完全正常** | 问题一定在我们的网络/编译产物 |
| 加法器通过、yolov5 失败 | NPU 可用但模型加载有问题 | 重点查 SDK 版本与权重上传 |
| 加法器就失败 | 位流/驱动/权限问题 | **先解决这个，别的都别做** |

> 这一步的价值：把"我们的 MVSplat 有问题"和"板子本身有问题"彻底分开。
> 仓库的历史记录里，这两者一直混在一起，是最费时间的地方。

## 6. 确认位流版本

```bash
# 看当前 BOOT 里的位流是哪一版
ls -la /boot/*.bit /boot/BOOT.bin 2>/dev/null
sha256sum /boot/*.bit 2>/dev/null
```

对照仓库里冻结的 `ai7030_edif_top_disable_icap.bit`（5,980,609 字节）。
**如果哈希不一致**，说明板子上跑的不是仓库验证过的那版位流——这本身就能解释很多异常。

⚠️ 同时要问清楚：**这个位流里有没有冻结渲染器？** 如果当前 BOOT 是"AI 版"（含 AI_Mate 但没渲染），
那 NPU 与渲染共存的问题就变成现实问题，而不是理论问题。

## 7. 编译 ARM 桥接（板子上，需要 SDK 头文件）

```bash
cd <repo>/examples/3dgs_reconstruction/mvsplat
python -m gaussian_generation.npu_branch.build \
    --sdk <SDK>/usr --out ARM_BUILD
```

**期望**：产出 `ARM_BUILD/libmgs_npu.so`。
若失败，看报错是"找不到头文件"（SDK 缺失）还是"编译器版本"（gcc 版本不匹配）。

## 8. 最小数值验证（板子上）

```bash
env -u LD_PRELOAD LD_LIBRARY_PATH=<SDK>/usr/lib/aarch64-linux-gnu \
python -m gaussian_generation.npu_branch.known_conv run \
    --graphs <known_conv 导出目录> --bundle <编译产物> \
    --library ARM_BUILD/libmgs_npu.so --out KNOWN_CONV
```

**这是仓库造的确定性小卷积**：identity / dyadic 两个用例要求**逐位相等**。
它能干净地区分"搬运/权重问题"和"舍入问题"。

- identity/dyadic 逐位相等 → 通路正确，可以进第 9 步
- 不相等 → 问题在权重上传或布局，与 MVSplat 无关，先修这个

## 9. 真实分区验证（板子上）

```bash
env -u LD_PRELOAD LD_LIBRARY_PATH=<SDK>/usr/lib/aarch64-linux-gnu \
python -m gaussian_generation.npu_branch.oracle_probe \
    --graphs graphs --bundle compiled --library ARM_BUILD/libmgs_npu.so \
    --partitions first_conv --diagnostic-continue --out PROBE
```

`--diagnostic-continue` 让它失败也不中断，把每个分区的输出都存成 `.npy`。

**然后把 `PROBE/*.npy` 和 `graphs/.../oracle.npz` 拷到 PC**，跑通道组归因：

```bash
python channel_group_attribution.py --oracle oracle.npz --actual first_conv_0.npy --markdown
```

## 卡点与责任分工

| 卡在哪 | 谁能解 |
|---|---|
| 找不到 SDK 运行时 | 厂商/负责人给 SDK 包 |
| 官方 demo 跑不起来 | 厂商（驱动/位流），或换回出厂 BOOT 验证 |
| 位流里没有 AI_Mate | 需要 Vivado 2018.03 + `AI_Mate.edif` 重新集成 |
| 编译产物缺失 | PC 上的 ICraft 编译器（`icraft-*.exe`），在 `npu_3dgs/.vendor/icraft-3.36.1/bin` |
| 数值仍不过 | 归因工具 → 定位到组 → 修权重上传或换 qdtype |

**最省时间的做法：先做第 5 步。** 加法器 demo 只要通，就说明板子没问题，
剩下的都是软件层面可解的；如果加法器都不通，后面所有工作都没意义。
