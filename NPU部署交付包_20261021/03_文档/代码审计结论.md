## 2. 定位到的具体机制：H1 会话地址冲突

`bridge.cpp` 里每个会话都走同一条路径：

```cpp
network = Network::CreateFromJsonFile(json);
network.lazyLoadParamsFromFile(raw);                       // ← 权重"懒加载"
...
session = Session::Create<ZG330Backend, HostBackend>(network, {device, host});
session.apply();                                           // ← 真正落设备
```

- 设备是**全局单例**：`Device::Open("axi://zg330aiu?npu=0x40000000&dma=0x80000000")`
  （`bridge.cpp:23`，基址写死）。
- 七个会话**共享同一个 device**，但各自独立 `apply()`。
- **桥接层完全没有对设备地址做任何偏移或分区控制**——权重落到 PL DDR 的哪一段、
  七个会话会不会落到同一段，完全由 SDK 内部决定，源码里看不到。

如果 SDK 的分配器不是全局唯一，后 `apply()` 的会话就会覆盖前一个的权重。
这与两个板端现象同时吻合：

1. `depth_head` 单会话正常、七会话非有限 → 后建的会话覆盖了它的权重
2. SDK `precheck()` 报 `The weight of opid:241 at PLDDR is incorrect` → 检查的正是 PLDDR 里的权重

**注意：这是机制推断，不是已证实的 bug。** 需要 §4 的实验判定。

## 3. 一个被忽略的判据：38.10% 这个比例本身

板端记录：真实网络第一层 38.10% 元素越界、两次结果一致。

这个数字比"max_abs"更有信息量：

- 如果是**整体布局错乱**（轴序错、padding 错），几乎全部元素都会错 → 越界比例应接近 100%
- 如果是**纯精度损失**，按 FP16 的 10 bit 尾数，相对误差约 5e-4，远小于 `rtol=2e-3` → 越界比例应接近 0%
- **实测 38.10%**，落在两者之间

这更像是：**一部分输出通道的权重正确、另一部分错误**（例如只加载了部分通道、
或通道分组错位）。这与"权重读回不正确"高度一致，而与"精度不够"不一致。

建议以后所有失败记录都带上越界比例，不要只报 `max_abs`（`tools/attribute_error.py` 已实现）。

## 4. 为此写的判定实验

`tools/session_isolation_test.py`（板端运行，无需 Torch、无需整网）：

```
每创建一个新会话 → 立刻重跑「第一个会话」的 oracle
```

判定规则：

| 现象 | 结论 |
|---|---|
| 被监测会话始终通过 | 无污染证据，问题在该分区自身（H2） |
| 创建某个会话后开始失败 | **污染成立**（H1），且记录是哪一个触发的 |
| 一开始就失败 | 与多会话无关，先修它自己 |

这个实验能一次区分两种情况，而 `verify.py` 的硬顺序（任一 oracle 失败即 raise）
导致这两种情况从来没被分开过。

## 6. 疑点：ICraft 的 `--qdtype tf32` 与"输出落在 FP16 格点"矛盾

`compile_graphs.py:61` 的精度档位是显式参数：

```python
p.add_argument("--qdtype", choices=("tf32", "fp16", "bf16", "fp32"), default="tf32")
```

仓库板端记录的是「TF32 内部计算、FP32 主机 I/O」，即按默认 `tf32` 编译。
但同一份报告写着：**NPU 输出 100% 落在 FP16 可表示的格点上**。

两者不能同时成立：

- 真按 TF32 算并 FP32 回传 → 输出不该是 FP16 格点
- 实际按 FP16 算或回传被转成 FP16 → **`--qdtype` 没有按预期生效**

这条比"精度够不够"更值得先问清楚，因为它决定后面所有精度讨论的前提。
三种可能，都需要 ICraft 的文档或厂商答复来区分：

1. `qdtype` 只影响量化阶段的标注，实际生成仍走 FP16 权重/激活
2. 生成阶段对某些算子强制 FP16（例如卷积单元只支持 FP16 通路）
3. `dump(stream,"SFB")` 在输出转换时降到 FP16

顺带：`bf16` 这一档**仓库从未试过**。它指数位与 FP32 相同（8 bit），
深层特征不易溢出，尾数 7 bit 比 FP16 的 10 bit 粗——对"范围敏感、精度不敏感"的
中间层往往比 FP16 稳。是否值得试，取决于上面三种可能是哪一种。
